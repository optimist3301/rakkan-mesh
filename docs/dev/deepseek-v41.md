# DeepSeek-V4.1-Flash: спецификация для движка

Этот документ — то, что движок `internal/llm` должен воспроизвести, чтобы
запустить DeepSeek-V4.1-Flash. Он написан по эталонному коду разработчиков,
а не по техническому отчёту: отчёт описывает идеи, код — арифметику.

- Эталон: `inference/` репозитория
  [deepseek-ai/DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash),
  ревизия `314113f8a7dadb388215396ba5fbee2c610a04d6`, лицензия MIT. Копия без
  изменений — в [`tools/llmref/dsv41/upstream`](../../tools/llmref/dsv41/upstream).
- Ссылки вида `model.py:766` ведут в эту копию
  (`tools/llmref/dsv41/upstream/inference/`).
- Инструменты и фикстура — в разделе 12.

**Узел работает без Python.** Импорт модели, токенизация, формат чата, хеш
Engram, подготовка изображений и вычисления — всё на Go. Python в этом
проекте — только инструмент разработки (`tools/llmref`): он снимает с
эталона значения, с которыми сверяются тесты Go. Всё, что эталон берёт из
библиотек Python (`tokenizers`, `numpy`, `sympy`, Pillow), движок реализует
сам и проверяет по этим значениям (раздел 12).

## 1. Где отчёт и код расходятся

- **CED — только конфигурация слоёв.** Слой 20 — источник сжатого KV для
  всего декодера, и строит он его из своего входа, то есть из выхода
  энкодера. Режима «промпт считает только энкодер, декодер — последние 128
  токенов» (Decoder SWA Bounded Replay) в эталоне нет: все 40 слоёв считают
  все токены. Bounded Replay — оптимизация сервиса, движок может добавить её
  позже как отдельный режим; результат будет детерминированным, но не равным
  эталону.
- **Промпт обрабатывается одним куском с позиции 0, дальше — по одному
  токену** (`model.py:709`, `:718`). Обработку промпта по частям эталон не
  определяет.
- **Цикл DSpark в эталоне отсутствует**: есть только прямой проход черновика
  (`model.py:129`). Правило принятия черновиков — наше.

- `compressor` и `head` эталон держит в f32, а `confidence_head.proj` в

- `mtp.*.embed` и `mtp.*.head` в чекпойнте отсутствуют: они общие с

E8M0 — это степень двойки: байт `e` означает `2^(e−127)`.

Значения E2M1 по 3-битному коду: 0, 0,5, 1, 1,5, 2, 3, 4, 6; бит 3 — знак.

## 4. Числовая модель

Эталон работает с `torch.set_default_dtype(bfloat16)`. Значения хранятся в
bf16 во всех местах, где тензор создаётся по умолчанию. Движок воспроизводит
**точки округления и квантования**; внутреннее устройство ядер GPU (порядок
сложения в тензорных ядрах) он не воспроизводит.

**Округление в bf16** — к ближайшему, при равенстве к чётному. Происходит:
- на выходе каждого матричного умножения;
- после RMSNorm, `hc_pre`, `hc_post`, Engram;
- на скалярных произведениях и сумме индексатора (раздел 6.4).

**`act_quant`: квантование активаций в FP8** (`kernel.py:41`). Перед каждым
FP8- и FP4-умножением вход квантуется блоками по 32 вдоль последней оси:

```
amax = max(|x_i|) по блоку, в f32;   amax = max(amax, 1e-4)
s    = 2^ceil(log2(amax · f32(1/448)))      # по битам f32: экспонента, +1 если мантисса ≠ 0
q_i  = E4M3(clamp(x_i / s, −448, 448))       # к ближайшему, при равенстве к чётному
```

Деквантованное значение `q_i·s` точно представимо в bf16. Режим `inplace`
пишет его обратно в тот же тензор; так квантуются окно SWA и выход
внимания перед `wo_a`.

**FP8-умножение** (`kernel.py:208`):

```
C[m,n] = Σ_k ( Σ_{j∈блок k} qa[m,j]·qw[n,j] ) · sa[m,k] · sw[n/32,k]
```

Сумма блоков идёт по `k` по порядку, в f32; результат округляется в bf16.
Значения FP8 кратны 2⁻⁹, поэтому сумма по блоку из 32 произведений точна в
int64/f64. Движок считает её точно, затем округляет в f32 один раз. На GPU
тензорные ядра складывают внутри блока со своей, неуточнённой точностью;
насколько это расходится с точной суммой, покажет `check_kernels.py`
(раздел 12).

**FP4-умножение** (`kernel.py:478`): то же, но вес FP4 с масштабом на
`(строку, блок k)`. Значения FP4·2 и FP8·2⁹ — целые, произведение меньше
2²²: блочная сумма точна в int32.

**`fp4_act_quant`: квантование в FP4** (`kernel.py:128`), два варианта:
- **E8M0, блок 32** (запрос и ключи индексатора):
  `amax = max(amax, 6·2⁻¹²⁶)`, `s = 2^ceil(log2(amax · f32(1/6)))`.
- **E4M3, блок 16** (сжатый KV):
  `amax = max(amax, 6·2⁻⁹)`, `s = E4M3(amax/6)` — масштаб сам округляется в FP8.

В обоих: `q = E2M1(clamp(x/s, −6, 6))` к ближайшему, при равенстве к чётному
коду. Знак сохраняется, так что возможен −0. В модели всегда используется
`inplace`: в тензор записывается `q·s`, в bf16 это точно.

**RMSNorm** (`model.py:281`): `x` в f32, `x·rsqrt(mean(x²)+1e-20)`, затем
умножение на вес (bf16, расширенный до f32), затем округление в bf16.

**RoPE** (`model.py:369`, `:392`). Пары соседних каналов `(x₂ᵢ, x₂ᵢ₊₁)`
поворачиваются как комплексные числа, в f32, и результат округляется обратно.
Важно: это **соседние пары, а не половины вектора** — не так, как в Llama.
Поворачиваются последние `rope_head_dim` каналов.

Частоты: `fᵢ = 1/θ^(2i/dim)`, `i < dim/2`. С YaRN (у слоёв со сжатием):

```
corr(r) = dim·ln(L₀/(2π·r)) / (2·ln θ)
low  = max(floor(corr(β_fast)), 0);  high = min(ceil(corr(β_slow)), dim−1)
ramp = clamp((i − low)/max(high − low, 1e−3), 0, 1)
fᵢ'  = fᵢ/factor · ramp + fᵢ · (1 − ramp)
```

Здесь L₀ — исходная длина 65536, factor = 16, β_fast = 32, β_slow = 1.
Угол `pos·fᵢ'`, считается в f32 (`torch.outer`, затем `polar`).

**Реализация в движке** — `internal/num/mx.go`: форматы, квантование
активаций (`QuantizeActFP8`, `ActQuantInPlace`, `QuantizeFP4`,
`FP4QuantInPlace`) и умножения (`MatVecFP8`, `MatVecFP4`).
- Блочные суммы точны, поэтому векторный код (`mx_amd64.s`, AVX2 и FMA) и
  портативный совпадают побитово при любом порядке сложения.
- FP4-блок считается в int32 (код ×2 на значение FP8 ×2⁹), FP8-блок — в
  float64.
- Коды NaN у E4M3 векторный код читает как 480, поэтому веса проверяются при
  импорте (`ValidE4M3`).
- Тесты сверяют всё побитово со значениями `kernel_cpu`
  (`internal/num/testdata/dsv41-mx.json.gz`, генератор
  `tools/llmref/dsv41/num_vectors.py`), включая сумму в f32 до округления в
  bf16: порядок сложения блоков виден только в ней.

**Выбор top-K.** Эталон вызывает `torch.topk`, а он ничего не гарантирует
при равных значениях. Равенства не редкость: оценки индексатора округлены
в bf16, а ReLU даёт много нулей. **Правило движка: из равных выигрывает
меньший индекс; выбранные упорядочены по убыванию оценки.** Эталонные дампы
сняты с тем же правилом (`tools/llmref/dsv41/run.py`). На фикстуре
равенство на границе top-K встречается в 6 вызовах из 233.

## 5. Прямой проход

Порядок задаёт `Transformer.forward` (`model.py:1245`):

1. **Эмбеддинг.** `h = embed[ids]` (bf16), копируется в 4 потока: `h[t, c] = e[t]`.
2. **Начальное смешивание.** `pre_mix = (1, 0, 0, 0)` — унитарный вектор.
3. **Хеши Engram** считаются по токенам заранее (раздел 8).
4. Для каждого слоя `i`:
   1. если в слое есть Engram: `h = engram(h, хеши)`;
   2. если `i` — целевой слой DSpark (37–39): запомнить `mean_c h` (в bf16) как вход черновика;
   3. `h, pre_mix = block(h, pre_mix)`.
5. **Голова.**
   - `x = Σ_c pre_mix[c]·h[c]` в f32, затем bf16 (`hc_pre`).
   - `x = RMSNorm(x)`.
   - `logits = x · headᵀ` в f32, только для последней позиции.

**Блок** (`model.py:970`), с потоком `X` (4×dim) на входе:

```
(a_pre, a_post, a_comb) = mixes(X, hc_attn_*)        # коэффициенты из входа блока
y  = attention(RMSNorm(hc_pre(X, pre_mix)))          # pre_mix — от предыдущего блока
X  = hc_post(y, X, a_post, a_comb)
(f_pre, f_post, f_comb) = mixes(X, hc_ffn_*)
y  = moe(RMSNorm(hc_pre(X, a_pre)))                  # a_pre — от внимания этого блока
X  = hc_post(y, X, f_post, f_comb)
return X, f_pre                                       # f_pre смешает вход следующего блока
```

Каждое смешивание входа берёт коэффициенты, посчитанные предыдущим подблоком:
это и есть Single-Pass mHC из отчёта.

## 6. Внимание

Обозначения: `x` — вход подблока внимания (bf16, после `attn_norm`), `rd = 64`,
`win = 128`, `m` — коэффициент сжатия слоя.

### 6.1 Запрос и окно

```
qr = RMSNorm(wq_a · x)                               # 1280, FP8-умножение
q  = (wq_b · qr) как [64 головы, 512]; RoPE на последние rd каналов каждой головы
kv = RMSNorm(wkv · x)                                # 512; RoPE на последние rd; act_quant inplace (FP8 по 32)
```

Окно SWA хранится кольцом из `win` строк.
- **Промпт** из `s` токенов: запрос `t` видит строки `max(0, t−win+1) … t`
  текущего куска (`model.py:410`), а KV здесь — все `s` строк куска. В кольцо
  записываются последние `win` строк так, что позиция `p` лежит в ячейке
  `p mod win`.
- **Шаг генерации** на позиции `p`: строка пишется в ячейку `p mod win`, и
  запрос видит всё кольцо от самой старой ячейки. Ячейки с позициями
  больше `p` (кольцо ещё не заполнено) помечены −1.

### 6.2 Компрессор (только источники KV)

Скрытый вектор относится к первому токену своей группы: группа `j` получает
позицию `j·m`.
- **m = 1:** `c = RMSNorm(wkv · x)`, `wkv` в bf16.
- **m = 2:** в f32 считаются `k = wkv·x` и `g = wgate·x` (веса f32, точно
  расширенные из bf16). Для каждого канала берётся softmax по `m` токенам
  группы, и `c = RMSNorm(bf16(Σ k·softmax(g)))`.
  - На промпте неполная последняя группа ждёт в состоянии.
  - При генерации вектор выходит, когда `(p+1) mod m = 0`, и его позиция
    `p+1−m`.

Затем, по порядку:
1. Ключ индексатора (только источники KV): `k_idx = RMSNorm(wk · c)`, 128
   каналов, RoPE на последние rd, `fp4_act_quant` (E8M0, блок 32).
2. Сжатая запись: RoPE на последние rd каналов `c`, затем `fp4_act_quant`
   (E4M3, блок 16).

Ключ индексатора строится из `c` **до** поворота.

### 6.3 Видимость

На промпте запрос `t` видит `⌊(t+1)/m⌋` сжатых записей, при генерации —
`⌊(p+1)/m⌋`. Индексы сжатых записей в общем списке KV сдвинуты на число
строк окна: при обработке промпта это `s`, при генерации — `win`.

### 6.4 Индексатор (источники индексов)

```
q_i = (indexer.wq_b · qr) как [32, 128]; RoPE на последние rd; fp4_act_quant (E8M0, 32)
w   = bf16( bf16(indexer.weights_proj · x) · (128^−0.5 · 32^−0.5) )  # [32]; множитель в f32
a_h = bf16( ReLU(bf16(q_i[h] · k_idx[t])) · w[h] )
score[t] = bf16( Σ_h a_h )                                            # сумма в f32, округление один раз
```

Округления в bf16 возникают потому, что кэш ключей и веса голов хранятся в
bf16 (`model.py:557`). Каждая операция PyTorch над bf16 считает в f32 и
округляет результат один раз. Невидимые позиции получают −∞. Слои Reindex берут
`k_idx` у последнего источника KV.

**Пул кандидатов** (слой 20, `model.py:584`):
- Оценка блока из 8 позиций — максимум оценок его позиций; хвост
  дополняется −∞.
- Блок, где лежит новейшая видимая позиция, закрепляется (+∞).
- Берутся 2048 лучших блоков; блоки с −∞ не берутся.
- Слои > 20, которые сами считают индексы, ставят −∞ всем позициям вне пула.

**Top-K:** `k = min(512, видимых записей)` по правилу из раздела 4.
Выбранные сортируются по позиции. Невидимые становятся −1, остальные
сдвигаются на смещение из 6.3.

Режим Reuse: слой берёт индексы последнего источника индексов как есть.

### 6.5 Собственно внимание (`kernel.py:311`)

Для каждой головы набор строк — окно плюс выбранные сжатые записи, строка
служит и ключом, и значением:

```
s_j = (q·kv_j) · 512^−0.5                    # f32; −∞ для индекса −1
o   = Σ_j e^(s_j−M) · kv_j / ( Σ_j e^(s_j−M) + e^(sink−M) )
```

M — максимум по `j`, без sink; если ни одного индекса нет, M = −1e30 и
`o = 0`. Эталонное ядро считает online-softmax блоками по 64 индекса и
округляет вероятности в bf16 перед умножением на значения. CPU-эталон
повторяет это.

Затем:
1. обратный RoPE на последние rd каналов выхода каждой головы (с той же позицией, что у запроса);
2. 64 головы группируются в 8 групп по 8;
3. `act_quant` inplace;
4. группа `g`: `wo_a[g] · o_g` → 1024, умножение bf16 на bf16 (`model.py:789`);
5. `wo_b · concat` → 5120.

## 7. MoE (`model.py:794`)

```
z      = gate.weight · x                    # f32 (вес bf16 расширяется)
score  = sqrt(softplus(z))
выбор  = top-6 по score + bias              # bias_vl для токенов изображений
w      = score[выбор] / (Σ score[выбор] + 1e−20) · 1.5      # сумма в порядке выбора
```

**Эксперт:**

```
g = f32(w1·x),  u = f32(w3·x)
u = clamp(u, −10, 10),  g = min(g, 10)
y = w2 · bf16( w · (silu(g) · u) )          # именно в этом порядке, в f32
```

Сумма выходов копится в f32 в порядке номеров экспертов по возрастанию,
затем прибавляется общий эксперт; результат округляется в bf16. Общий
эксперт — FP8, маршрутизируемые — FP4.

## 8. Engram (`model.py:328`, `engram.py`)

**Хеш.** Таблицы хеша движок строит сам, на Go, при импорте модели; они
зависят только от токенайзера и конфигурации:
- **Карта сжатого словаря** (`build_compressed_token_map`). Каждый токен
  декодируется в текст. Если в тексте есть U+FFFD (кусок UTF-8), ключом
  служит сама строка токена. Иначе ключ — текст после цепочки нормализаций
  `tokenizers`: NFKC, NFD, удаление всех знаков категории M — Mn, Mc и Me,
  включая гласные-знаки индийских письменностей (StripAccents),
  нижний регистр, замена пробельных серий `[ \t\r\n]+` на пробел,
  сохранение токена из одного пробела, обрезка пробелов по краям. Пустая
  нормализация заменяется исходным текстом. Номера ключам выдаются в
  порядке первого появления. У настоящей модели 129280 токенов дают 99092
  ключа, и любое расхождение меняет все хеши.
- **Простые числа**: для каждого слоя Engram, длины n-граммы и головы по
  порядку — наименьшее простое больше `engram_vocab_size − 1` (для следующей
  головы — больше предыдущего), не выданное раньше.
- **Множители**: `numpy.random.default_rng(10007 · layer_id).integers(0,
  bound, 4, int64)·2 + 1`, где `bound = (2⁶³−1) // vocab // 2`, а `vocab`
  — размер сжатого словаря. Движку нужна точная копия генератора numpy:
  SeedSequence, PCG64 и ограниченные целые (метод Лемира).

Готовые значения для настоящей модели лежат в
`internal/llm/testdata/dsv41-vectors.json.gz`, для крошечной — в
`engram.json` фикстуры. Это эталоны для тестов, а не входные данные узла.

Дальше хеш — целочисленная арифметика.
1. Токены переводятся в сжатый словарь (`token_map`, 99092 значения у
   настоящей модели). Токены изображений помечаются как «мёртвые».
2. Для позиции `p` берутся токены `p, p−1, p−2, p−3`. Начиная с позиции до
   начала текста или первого мёртвого токена, все дальше заменяются на
   `pad_id`.
3. `prod_k = tok_k · mult_k` в int64 (переполнения нет по построению).
4. Скользящий `r = prod_0 XOR prod_1 …`. После XOR с `prod_k`
   (n-грамма длины k+1) для каждой головы `h` строка таблицы:
   `r mod prime[k−1][h] + offset[k−1][h]`.

Получается `3·8 = 24` строки на позицию, в порядке «длина n-граммы, затем голова».

**Применение** — до блока, к четырём копиям потока `h`:

```
e     = bf16(FP8-строки · масштабы), склеенные: 24·256 = 6144
kv    = engram.wkv · e                    # 5·dim: ключ на копию и общее значение
key_c = kv[c·dim:(c+1)·dim], value = kv[4·dim:]
r_c   = rsqrt(mean(h_c²)+ε) · rsqrt(mean(key_c²)+ε)
d_c   = Σ(h_c · q_weight_c·k_weight_c · key_c) · r_c · dim^−0.5
gate_c = sigmoid(sign(d_c) · sqrt(max(|d_c|, 1e−6)))
h_c   = bf16(h_c + gate_c · value)
```

Для токенов изображений гейт равен 0.

## 9. mHC (`model.py:950`, `kernel.py:407`)

Входной поток — 4·dim, в f32:

```
r      = rsqrt(mean(X²) + 1e−20)
mix    = (hc_fn · X) · r                     # 24 числа
pre_c  = sigmoid(mix_c · scale₀ + base_c) + 1e−6
post_c = 2·sigmoid(mix_{4+c} · scale₁ + base_{4+c})
C_jk   = mix_{8+4j+k} · scale₂ + base_{8+4j+k}
C      = softmax_k(C) + ε;  C = C / (Σ_j C + ε)
повторить 19 раз: C = C / (Σ_k C + ε);  C = C / (Σ_j C + ε)
```

**`hc_pre(X, p)`** = `bf16(Σ_c p_c·X_c)`.

**`hc_post(y, X, post, C)`**: копия `k` нового потока равна
`bf16(post_k·y + Σ_j C_jk·X_j)`.

## 10. DSpark

Черновик — 3 блока (`mtp.0–2`), только окно, свой MoE: 128 экспертов, на токен 3.

**Вход:**
- склеенные средние `mean_c h` на входе слоёв 37–39 → `main_proj` →
  RMSNorm — это `main_x`;
- первый токен черновика — последний принятый, остальные 4 — `noise_token_id`.

**Устройство:**
- KV окна черновика строится из `main_x`, а запросы — из его собственных блоков.
- Голова общая с моделью.
- Голова Маркова: эмбеддинг ранга 256 и выход на словарь; на позиции `i` к
  логитам прибавляется её выход для токена `i`.
- Голова уверенности: линейный слой на `[скрытое, марковский эмбеддинг]`.

Что делать с черновиком, эталон не определяет (раздел 1).

## 11. Токенизатор и формат чата

**Токенизатор.** Byte-level BPE, 128000 токенов, 127741 слияние, 1283
добавленных; нормализатора нет (в отличие от Qwen — без NFC). Разбиение
идёт в три последовательных прохода:
1. `\p{N}{1,3}`;
2. `[一-龥぀-ゟ゠-ヿ]+`;
3. `[!"#$%&'()*+,\-./:;<=>?@\[\\\]^_`{|}~][A-Za-z]+|[^\r\n\p{L}\p{P}\p{S}]?[\p{L}\p{M}]+| ?[\p{P}\p{S}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+`.

Затем ByteLevel без своего регулярного выражения. Специальные токены:
`<｜begin▁of▁sentence｜>` (0), `<｜end▁of▁sentence｜>` (1, он же pad).

**Формат чата.** `upstream/encoding/encoding.py`, с тестами в
`encoding/tests`. Режим рассуждения задаётся числом 1–100.

**Реализация на Go:**
- **Токенайзер** — `internal/llm/bpe`. Три разбиения: первые два через
  `regexp`, третье (с lookahead) разобрано вручную.
- **Формат чата** — `internal/llm/dsv41/chat.go`, порт `encoding.py`.
  - Схемы инструментов и аргументы вставляются в промпт через Python
    `json.dumps`. Поэтому сообщения обрабатываются как JSON с семантикой
    Python (`pyjson.go`): порядок ключей сохраняется, числа печатаются как
    `repr` Python (`1e-05`, `1000.0`, `1e+16`), разделители `", "` и `": "`.
  - Сохранены и неочевидные места эталона: результат инструмента с
    `content: null` пишется как `None`, результаты сортируются по порядку
    вызовов устойчивой сортировкой, а неизвестный идентификатор получает
    позицию 0.
- **Проверка:** 421 текст токенизации и 374 случая формата чата плюс 17
  разборов ответа совпадают с эталоном.

## 12. Инструменты и фикстура

Всё — в [`tools/llmref/dsv41`](../../tools/llmref/dsv41), подробности в его
README.

**`kernel_cpu.py`** — замена ядер tilelang на PyTorch для CPU, чтобы эталон
работал без GPU. Квантование повторено операция за операцией, блочные суммы
считаются точно. `test_kernel_cpu.py` сверяет его с прямыми определениями.

**`tiny.py`** строит крошечную модель со всеми механизмами настоящей:
- 8 слоёв: 0–1 окно; 2–4 энкодер с m = 2 (2 — источник, 3–4 — Reuse);
  5–7 декодер с m = 1 (5 — источник и пул кандидатов, 6 — Reuse, 7 — Reindex);
- Engram в слоях 1 и 4;
- слой DSpark;
- ширина 128, словарь — первые 512 токенов настоящего;
- окно 8, top-8, пул из 3 блоков по 4 позиции.

Веса записываются в формате настоящего чекпойнта, конвертируются его же
`convert.py` и загружаются, как `generate.py`. Результат —
[`internal/llm/testdata/dsv41-tiny`](../../internal/llm/testdata/dsv41-tiny),
около 4 МБ:
- `model.safetensors` и `config.json` — в схеме настоящих;
- `inference.json` — аргументы эталона;
- `engram.json` — таблицы хеша;
- `golden.safetensors` — эталонные выходы.

**Что лежит в `golden.safetensors`.** Прогон с подстановкой токенов (teacher
forcing): промпт из 23 токенов, затем 17 шагов генерации. Для каждого шага:
- логиты;
- поток и `pre_mix` после каждого блока;
- выход Engram и выход внимания слоёв-источников;
- индексы top-K и пул кандидатов;
- черновик DSpark;

а в конце — кэши слоёв.

Генерация детерминирована: повторный запуск даёт побитово те же файлы.

**`vectors.py`** снимает эталонные значения того, что эталон считает
библиотеками Python, для настоящей модели. Результат —
`internal/llm/testdata/dsv41-vectors.json.gz`, 364 КБ:
- полная карта сжатого словаря Engram;
- простые числа, смещения и множители хеша, а также множители для слоёв
  0–63 — это проверка порта генератора numpy;
- хеши n-грамм для набора текстов;
- токенизация этих текстов (CJK, цифры, пробельные серии, диакритика,
  эмодзи, специальные токены).

Формат чата сверяется прямо с тестами эталона в
`upstream/encoding/tests`.

**`check_kernels.py`** — проверка на машине с NVIDIA GPU (Hopper или
Blackwell):
- сравнивает ядра tilelang с `kernel_cpu` на размерах настоящей модели;
- прогоняет фикстуру на GPU и сверяет с эталоном CPU.

Квантование обязано совпасть побитово; для умножений и внимания отчёт
показывает долю совпадающих значений и наибольшую ошибку. Флаг `--dry-run`
проверяет сам скрипт без GPU.

## 13. Состояние реализации

Пакет `internal/llm/dsv41` считает основную часть модели в одном процессе:
- mHC, внимание (окно, CSA2 во всех трёх режимах, индексатор, пул кандидатов);
- MoE, Engram, голова.

Модель режется на стадии конвейера по сети (этап 5, ниже). DSpark и
изображения — следующие этапы.

**Обработка промпта.** Позиции промпта считаются по одной, как при генерации.
Совпадение с пакетной обработкой эталона обеспечено тем, что каждая
позиция видит ровно то же, что в эталоне. Единственное отличие промпта от
генерации — раскладка индексов окна (раздел 6.1): от неё зависит группировка
online-softmax.

**Сверка с фикстурой:**
- С подстановкой эталонного потока после каждого блока:
  - в каждом слое не меньше 99,9% значений потока совпадают побитово,
    остальные — на 1–3 единицы последнего разряда bf16;
  - все выборы индексатора совпадают;
  - выбранный токен совпадает на всех шагах.
- Engram совпадает побитово.
- Логиты на amd64 (AVX2) и arm64 (портативный код) одинаковы побитово —
  тест сравнивает хеш.

**Свободный прогон расходится с эталоном, и это неустранимо.** Перед каждым
умножением активации квантуются в FP8 (3 бита мантиссы). Разница в одну
единицу bf16 может перевести значение через границу округления FP8, а
максимум блока — через степень двойки, и тогда меняется масштаб 32
значений. Расхождение начинается уже на второй позиции промпта.
- На фикстуре совпадает 93 из 120 выборов индексатора и выбранный токен на
  15 шагах из 18.
- Так же разойдутся любые две реализации эталона, в том числе его прогоны
  на GPU и на CPU.

Поэтому корректность проверяется с подстановкой, а между узлами сети
совпадение обеспечивает детерминизм движка.

**Проверка на настоящих весах (этап 4).** Слои 2 (энкодер, m = 2, источник
KV и индексов) и 20 (декодер, m = 1, пул кандидатов) из опубликованного
чекпойнта. На вход подаются эмбеддинги 1106 токенов настоящего текста: 1100
позиций промпта и 6 шагов генерации. Этого хватает, чтобы задействовать то,
чего не достаёт крошечная фикстура:
- сжатых записей больше, чем отбирает top-512;
- окно в 128 позиций переполняется;
- внимание идёт по 10 блокам по 64 записи.

Эталон — `tools/llmref/dsv41/layer_check.py`, тест — `real_test.go`. Тест
запускается, только если задана переменная `RAKKAN_DSV41_REAL`: шард слоя
весит 6,9 ГиБ.

Внимание и MoE проверяются по отдельности, каждый на эталонном входе.

| | Слой 2 | Слой 20 |
|---|---|---|
| Внимание, L2-ошибка (при совпавшем выборе) | ≤ 1,3% | ≤ 0,7% |
| Выбор индексатора совпадает | 1106 из 1106 | 1098 из 1106 |
| Кэш сжатого KV / ключей индексатора | 100% / 100% | 100% / 3 значения из 141 568 |
| MoE, L2-ошибка | ≤ 0,17% | ≤ 0,35% |
| Набор экспертов совпадает | везде | везде |

По шагам внимания слоя 2 видно, где возникает расхождение:
- запрос, его поворот и запись окна совпадают практически побитово;
- выход softmax-внимания изредка отличается на одну единицу bf16 (это
  `exp` и f32-суммы);
- два квантования в FP8 (перед `wo_a` и `wo_b`) усиливают это до ~1% L2.

**Слой 20.** Два ключа индексатора отличаются от эталонных на один шаг
сетки FP4 (`0` против `0.25`). Отсюда 6 из 8 расхождений выбора: это замена
этой записи на соседнюю по оценке на границе top-512.

**Сдвинутые RoPE.** Если подставить эталонную таблицу `cos`/`sin`, ничего не
меняется: наши значения отличаются не больше чем на 6·10⁻⁸.

**`wo_a`.** Точное FP8-умножение движка вместо `einsum` эталона в bf16 даёт
разницу не больше 1–2 единиц bf16 в нескольких значениях — разный порядок
сложения.

**Тест различает округление и ошибку.** Пропущенный sink даёт L2-ошибку
внимания 0,85, забытый множитель маршрутизации — L2-ошибку MoE 0,32, а
пороги теста — 0,03 и 0,01. Целый блок отличается до 7–23% L2, потому что
расхождения складываются через квантование; это записывается для справки.

**Конвейер по сети (этап 5).** Модель режется на стадии между любыми слоями.
Что передаётся между стадиями (`dsv41.Payload`, `stage.go`):
- поток mHC `[4][dim]` в bf16 и `pre_mix` следующего блока;
- строки таблиц Engram для n-грамм позиции: хеширует координатор, у которого
  есть история токенов и таблицы хешей (строятся из токенайзера);
- номер последнего пройденного источника KV и записи, добавленные им в свои
  кеши на этой позиции (сжатый KV и ключ индексатора), если группа
  закончилась;
- выбор top-k последнего источника индексов и пул кандидатов (как список
  блоков).

Слои после источника KV читают его кеши целиком. Поэтому стадия хранит копию
кешей источника, стоящего перед её первым слоем, и дополняет её записями из
`Payload`. Этого достаточно: выбор и пул кандидатов считаются заново на
каждой позиции, а кеши растут не больше чем на запись за позицию.

Стадия проверяет входящий `Payload`:
- размеры совпадают с конфигом;
- источник KV — тот, что стоит перед её первым слоем;
- выбранные записи есть в её копии кеша;
- позиции идут по порядку.

Испорченный `Payload` даёт ошибку, а не панику.

**Проверка разбиения.** `TestStagesMatchOneProcess` перебирает все 128
разбиений 8 слоёв фикстуры на последовательные стадии. Для каждого разбиения
`Payload` передаётся как байты, одна стадия заменяется посреди промпта,
другая — посреди генерации, и замена переигрывает свои входы. Логиты на всех
позициях совпадают с однопроцессным прогоном побитово, на amd64 и на arm64.

Тест ловит потерю пула кандидатов и одной записи выбора при передаче.

**По сети** (`internal/llm/deepseek_test.go`), на фикстуре с её токенайзером,
урезанным до 512 токенов:
- на трёх узлах (разрезы 0–3 | 3–6 | 6–8: внутри группы источника 2 и между
  источником 5 и его потребителями) получается тот же текст, что в одном
  процессе;
- с четырьмя отказами стадий текст тот же;
- свидетель ловит один перевёрнутый бит в конце `Payload`, то есть в общем
  состоянии внимания, а не в потоке.

**Хранение.** Манифест версии 2 (`arch: "dsv41"`) содержит `config.json`
модели и следующие блобы:
- по блобу на блок (safetensors с тензорами чекпойнта);
- голова (эмбеддинг, `norm`, `head`);
- `tokenizer.json`;
- для слоёв Engram — таблица отдельным блобом (строки, затем масштабы).

Стадия читает таблицу из хранилища блобов по строкам, через `ReaderAt`.
Импорт (`llm.ImportDeepSeek`, HTTP — `POST /v1/llm/models` с `format: hf`)
копирует тензоры потоково, по блоку. Затем он загружает каждый блок и голову
один раз для проверки (так же проверяется, что токенайзер сжимается для
Engram в нужное число id).

**Размеры настоящей модели** считаются по конфигу (`part.go`), для плана и
учёта памяти до загрузки:

| | Память | Читается на токен | Активных весов |
|---|---|---|---|
| Обычный блок | 6,9 ГиБ | 277–303 МиБ | 377–388 млн |
| Блок с Engram (1, 14) | 7,0 ГиБ + 94 ГиБ на диске | 428–454 МиБ | 535–545 млн |
| Все 40 блоков | 276 ГиБ + 189 ГиБ на диске | 11,2 ГиБ | 15,5 млрд |
| Голова (координатор) | 4,9 ГиБ | | |

- `Payload` — до 54 184 байт на токен.
- Кеши стадии из 20 слоёв на 8192 позиции — около 35 МиБ.
- Генерация без `max_tokens` ограничена 4096 токенами: иначе каждая стадия
  резервировала бы кеши на миллион позиций контекста.

Планировщик учитывает у каждого слоя память, байты на токен и место на диске.
Узел объявляет место в хранилище блобов (`free_disk`). Газ стадии — 8 на
активный вес.

**GPU (этап 7).** Блок целиком считается на Vulkan
(`internal/llm/dsv41/gpu.go`: `Model.ToGPU`, `GPUPart.NewStage`,
`GPUStage.Forward`) и даёт тот же `Payload`, что `Stage.Forward`, побитово.
Ядра — в `internal/gpu` (`mx.go`, `dsops.go`, `crmath.go`); как они
повторяют CPU, описано в [ARCHITECTURE.md](../ARCHITECTURE.md), в разделе про GPU.

Проверено на фикстуре при любом разбиении на стадии (RADV и lavapipe) и на
настоящих слоях 2 и 20: на всех 1106 позициях побитово. На встроенной Vega
позиция слоя считается за 34–39 мс против 55–59 мс на CPU.

Чтобы GPU мог повторить CPU, изменён один расчёт CPU: softplus в
маршрутизаторе теперь `num.Log1p32` на `float32` вместо `log1p` в `float64`.
Хеш логитов фикстуры от этого не изменился.

В сетевом конвейере узел с GPU считает свои слои DeepSeek на нём
(`llm.Service`). Веса уходят в видеопамять, копия в RAM освобождается. GPU-
и CPU-узлы смешиваются в одном конвейере и подменяют друг друга при отказе.

Узел, которому слои целиком не помещаются в видеопамять, держит на GPU их
плотную часть (около 7 ГиБ на модель), а эксперты — в RAM, и считает их на CPU
(`GPUOptions.HostExperts`). Выбор top-k индексатора линеен по числу записей.

**Пакетная обработка** (`GPUStage.ForwardBatch`, до `GPUBatch` = 8
позиций). Пакет проходит слой целиком, затем следующий слой. Это эквивалентно
последовательному счёту: позиция зависит от предыдущих только через кеши того
же слоя.
- **FP8-произведения** плотной части (`wq_a`, `wq_b`, `wkv`, `wo_a`, `wo_b`,
  `wq_b` индексатора, общий эксперт, `wkv` Engram) читают веса один раз на
  пакет. Каждая пара «строка × позиция» складывает те же слагаемые в том же
  порядке.
- **По одной позиции, по порядку**: компрессор, индексатор, выбор,
  разреженное внимание.
- **Окно пакета** лежит в отдельном буфере и переносится в кольцо после
  пакета, иначе поздние позиции затёрли бы слоты, нужные ранним. Открытая
  группа компрессора тоже переносится.
- **Эксперты** выбираются для каждой позиции, и все 6·8 считаются одной
  отправкой.
- **В сервисе** стадия на GPU берёт промпт и повтор входов после отказа
  пакетами.

Проверено: на фикстуре пакеты по 3, 5 и 8 позиций (внутри промпта, через его
конец, в генерации) дают побитово те же `Payload`, что CPU. Три внесённые
ошибки (окно пакета, перенос группы компрессора, перенос окна в кольцо)
ловятся. На настоящих слоях 2 и 20 пакеты тоже совпадают побитово на всех 1106
позициях. Позиция промпта на Vega стала 26–29 мс вместо 31–34. Пакет не
сокращает внимание и экспертов (у позиций они разные), поэтому дальше
ускорять нужно их.

Этап 7 завершён: на любом GPU с Vulkan 1.1 слой считается целиком или с
экспертами в RAM, в сетевом конвейере, побитово как на CPU.

**Импорт с Hub (этап 6).** Модель на 467 ГиБ не проходит через один узел.
- **Импорт** (`llm.ImportHub`, HTTP — `format: "hub"`) скачивает только
  `config.json`, индекс и токенайзер. Ветка закрепляется как коммит. Манифест
  (10 КБ) хранит размер и хеш каждого из 45 нужных файлов и то, в каких файлах
  голова и каждый слой. Например, слой 1 — шарды 4 и 47, последний с таблицей
  Engram.
- **Узел стадии** получает только файлы своих слоёв (`sources.go`): из
  хранилища блобов, если они там, иначе у участника, который их объявил, иначе
  с Hub. Байты из любого источника хешируются и должны совпасть с закреплённым
  хешем, так что участник не может подсунуть другой файл. Загрузка с Hub при
  обрыве продолжается запросом Range. Если запрос, начавший её, сдался,
  загрузка идёт дальше в фоне, а следующий запрос её застаёт.
  `POST /v1/llm/prefetch` скачивает заранее.
- **Файлы хранятся в хранилище блобов как есть.** Тензоры слоя читаются из них
  напрямую, а таблица Engram — на месте, без копии.
- **Индекс «хеш → блоб»** переживает перезапуск (`hub-files.json` в каталоге
  данных). Объявленные файлы видны другим узлам.

Проверено:
- на поддельном Hub в `httptest` с фикстурой, разложенной как настоящий
  репозиторий: импорт не трогает веса; на двух узлах каждый скачивает только
  файлы своих слоёв, ровно один раз, текст — как у одного процесса; оборванная
  загрузка докачивается вторым запросом; поздний узел берёт файлы у
  участников; неверные байты с Hub и чужой файл под нужным хешем отвергаются;
- на настоящем Hub: манифест DeepSeek-V4.1-Flash совпадает с закреплёнными
  хешами инструментов на всех 45 файлах (`RAKKAN_HUB_ONLINE=1`). Часть
  координатора собирается из скачанных и проверенных шардов 2 и 43 (2,5 ГиБ за
  4 мин 52 с) и считает логиты промпта (`RAKKAN_HUB_ONLINE=head`).

## 14. Открытые вопросы

- **Чтение строк Engram с диска.** Каждая строка читается через `ReaderAt`
  блоба, а это файл чанка в 1 МиБ с проверкой SHA-256. Получается 48 чанков
  на токен на слой Engram. Это заметные десятки миллисекунд. Кеш чанков или
  проверка хеша один раз при загрузке сняли бы эту цену.
- **Пакетный prefill.** Стадия считает позиции промпта по одной, как и
  однопроцессный движок.

- **Сверка CPU-эталона с настоящими ядрами** ждёт машины с GPU. До неё
  точность `kernel_cpu` подтверждена только сравнением с прямыми
  определениями. Главный вопрос — побитовое совпадение квантования; расхождение
  блочных сумм тензорных ядер ожидаемо и должно быть мало.
- **Таблицы Engram, токенайзер и формат чата** готовы на Go (этап 2).
  Узлу из файлов DeepSeek нужны только чекпойнт, `config.json` и
  `tokenizer.json`.
- **Изображения** в фикстуру не входят: ViT, свёртка пикселей,
  `bias_vl` — этап 9. Эталон уменьшает картинку через Pillow
  (`image_processor.py:123`, `Image.resize` с фильтром по умолчанию).
  Движку нужна точная копия этого фильтра на Go, со своими эталонными
  значениями.
- **Правило принятия черновиков DSpark** — этап 8.
