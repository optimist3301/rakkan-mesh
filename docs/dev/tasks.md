# Задачи: как писать код, который исполняет сеть

Задача — это модуль WebAssembly. Узел-исполнитель загружает его в песочницу,
даёт ему вход и вызывает экспортированную функцию. Задача пишет выход и
возвращает код выхода. Этот документ описывает всё, что видит задача, и
правила, которым она должна следовать.

## Контракт модуля

Модуль принимается, если выполнено всё перечисленное:

- **Точка входа.** Экспортирует функцию `run` с сигнатурой `() -> i32` (или
  другую с той же сигнатурой, если клиент указал её в `entry`). Имена с
  префиксом `__rakkan_` зарезервированы.
- **Память.** Экспортирует свою линейную память под именем `memory`. Импорт
  памяти запрещён.
- **Импорты** только из пространств имён ниже, с точными сигнатурами. Всё
  остальное, включая WASI и `env`, отклоняется до запуска с ошибкой
  `forbidden_import`.

| Пространство имён | Capability | Что даёт |
|---|---|---|
| `rakkan` | — (есть всегда) | вход, выход, лог, прикреплённые блобы |
| `rakkan_image_v1` | `image/1` | нативная обработка изображений |
| `rakkan_tensor_v1` | `tensor/1` | нативные матричные операции |
| `rakkan_randomx_v1` | `randomx/1` | хеш RandomX (Monero) |

Задачи с импортами из `rakkan_image_v1` или `rakkan_tensor_v1` планировщик
отправляет только на узлы, объявившие соответствующую capability (видно в
`status().load.capabilities`).

- **Возможности WebAssembly.** Поддерживается WebAssembly 2.0: SIMD128,
  bulk memory, multi-value, расширение знака, преобразования без ловушек,
  ссылочные типы. Не поддерживаются потоки (shared memory) и memory64.
- **Структурные лимиты** (защита компилятора от модулей, которые дорого
  компилировать):

| | Лимит |
|---|---|
| размер тела функции | 1 МиБ |
| функций, типов, глобальных переменных, экспортов, сегментов | по 100 000 |
| импортов | 1 000 |
| локальных переменных в функции | 50 000 |
| вложенность блоков | 1 024 |
| целей `br_table` | 16 384 |
| параметров и результатов функции | 128 |

Обычные компиляторы (AssemblyScript, clang, rustc) в эти лимиты укладываются.
Компиляция модуля тоже засчитывается во время задачи.

## Базовый ABI (`rakkan`)

Все указатели — смещения в линейной памяти задачи. Выход за её границы
завершает задачу с ошибкой `memory_access`.

| Функция | Сигнатура | Что делает |
|---|---|---|
| `input_len` | `() -> i32` | размер входа в байтах |
| `input_read` | `(dst i32, offset i32, len i32) -> i32` | копирует до `len` байт входа начиная с `offset` в память по адресу `dst`; возвращает число скопированных байт |
| `output_write` | `(src i32, len i32)` | дописывает `len` байт в выход задачи. Сверх лимита выхода задача завершается с ошибкой `output_limit` |
| `log` | `(src i32, len i32)` | дописывает в диагностический лог. Лог сверх 64 КиБ обрезается (`log_truncated`), задача продолжается |

Выход можно писать по частям: вызовы `output_write` дописывают байты подряд.
Лог возвращается клиенту и в успешном результате (`logs`), и в тексте ошибки
(последний 1 КиБ), так что это основной инструмент отладки на удалённом узле.

## Прикреплённые блобы

Клиент может прикрепить к задаче до 16 блобов (параметр `blobs`). Задача
читает их кусками. Узел-исполнитель скачивает только те чанки по 1 МиБ,
которые задача действительно прочитала, и проверяет их хеши. Так задача
может работать с маленькой частью огромного файла.

| Функция | Сигнатура | Что делает |
|---|---|---|
| `blob_count` | `() -> i32` | число прикреплённых блобов |
| `blob_size` | `(index i32) -> i64` | размер блоба `index` в байтах, −1 если такого нет |
| `blob_read` | `(index i32, dst i32, offset i64, len i32) -> i32` | читает до `len` байт блоба начиная с `offset` в память; возвращает число байт, 0 в конце блоба, −1 если блоба нет |

Если блоб не удалось получить ни у одного источника, задача завершается с
ошибкой `blob_unavailable`. Это сбой не задачи, а сети: такую задачу сеть
повторяет на другом исполнителе.

Блобы — главный способ передавать задачам большие неизменяемые данные:
словари, веса моделей, файлы для обработки по диапазонам (см. шаблоны в
[distributed.md](distributed.md#общие-данные-прикреплённые-блобы)).

## Код выхода и ошибки

Есть два разных исхода:

1. **Задача завершилась** и вернула код выхода. `0` означает успех, любое
   другое число — ваш собственный сигнал: «не найдено», «вход некорректен» и
   т. п. Клиент получает результат с `exitCode`, выходом и логом. Это не
   ошибка: ненулевой код удобен, например, для ранней остановки
   (`stopOnExitCode`).
2. **Задача не смогла завершиться.** Клиент получает ошибку с полем `kind`:

| `kind` | Причина | Повторяется ли сетью |
|---|---|---|
| `out_of_gas` | исчерпан бюджет gas | нет: повтор дал бы то же |
| `timeout` | вышло время по часам | нет |
| `trap` | ловушка WebAssembly: `unreachable`, деление на ноль, выход за границы памяти в коде задачи, `abort` в AssemblyScript | нет |
| `memory_access` | указатель за границей памяти в вызове ABI | нет |
| `output_limit` | выход больше лимита | нет |
| `invalid_module` | модуль не разбирается или нарушает контракт | нет |
| `forbidden_import` | импорт вне разрешённого ABI | нет |
| `missing_entry` | нет точки входа или неверная сигнатура | нет |
| `module_too_large`, `input_too_large` | превышены лимиты размера | нет |
| `limit_policy` | запрошенные лимиты выше политики узла | пробуется другой узел |
| `blob_unavailable` | прикреплённый блоб недоступен | да |
| `worker_crashed`, `worker_oom`, `worker_protocol`, `internal`, `canceled` | сбой исполнителя | да (кроме `worker_oom`) |

Детерминированные ошибки (первые девять строк) сеть не повторяет: на любом
другом узле задача упала бы так же. Ошибки сети и самих клиентов
(`no_capacity`, `no_consensus` и другие) описаны в [SDK](sdk.md#ошибки).

## Gas и лимиты

**Gas** — детерминированная мера работы. При загрузке модуль переписывается
так, что каждый линейный участок кода списывает свою точную стоимость:

| Операция | Gas |
|---|---|
| большинство инструкций | 1 |
| вызов функции | 4 |
| вызов функции хоста (ABI) | 10 + 1 за каждые 16 переданных байт |
| `memory.grow` | 4096 за страницу 64 КиБ |
| bulk memory (`memory.copy`, `memory.fill`) | 1 за 16 байт |
| kernels изображений и тензоров | откалиброваны по времени работы, см. ниже |

Единица gas откалибрована примерно в 0,15 нс работы эталонной машины:
5·10⁹ gas (бюджет по умолчанию) — это около 0,75 с счёта. Одна и та же
задача с тем же входом тратит одинаковый gas на любом узле, поэтому gas
входит в результат, который сравнивают реплики.

**Лимиты задачи.** Клиент задаёт их в `limits`; незаданные поля берутся по
умолчанию:

| Лимит (поле SDK) | По умолчанию | Потолок узла по умолчанию |
|---|---|---|
| `gas` | 5·10⁹ | 5·10⁹ |
| `timeoutMs` (время по часам, включая компиляцию) | 10 000 | 10 000 |
| `memoryMB` (линейная память) | 64 | 64 |
| `maxInputBytes` | 16 МиБ, но не меньше размера входа | `-max-input-mb` (16) |
| `maxOutputBytes` | 16 МиБ | `-max-output-mb` (16) |
| размер модуля | 8 МиБ | 8 МиБ |
| лог | 64 КиБ | 64 КиБ |

Узел не берёт задачи, лимиты которых выше его потолка. Если такого узла нет
во всей сети, клиент получает `no_capacity` с объяснением, какой лимит
превышен. Сейчас у демона настраиваются только потолки входа и выхода.
Потолки gas, памяти и времени равны значениям по умолчанию, поэтому
**одна задача рассчитана примерно на секунду счёта и 64 МиБ памяти**.
Большую работу нужно резать на много задач, для этого сеть и создана
(см. [distributed.md](distributed.md#размер-задачи)).

Время по часам — страховка на случай, если gas не остановил задачу. Задачи
должны укладываться в gas, а не в время: время на разных узлах разное.

## Детерминизм и что запрещено

Сеть рассчитывает на то, что результат задачи — чистая функция модуля и
входа. Песочница обеспечивает это сама:

- **Нет недетерминированных источников.** У задачи нет часов, случайности,
  файлов, сети и переменных окружения.
- **NaN канонизируются.** Знак и полезная нагрузка NaN после арифметики на
  разных процессорах различаются, поэтому песочница заменяет любой NaN
  канонической формой. Арифметика с плавающей точкой в WebAssembly и так
  детерминирована: FMA нет, округление IEEE.
- **Gas детерминирован**, а время по часам в результат не входит.

Что это значит для кода задачи:

- **Нужна случайность** — используйте генератор псевдослучайных чисел, а
  зерно передавайте во входе. Разным задачам — разные зёрна. Пример:
  `sdk/as/examples/montecarlo.ts`.
- **Не полагайтесь на адреса и порядок хеш-таблиц**, если ваш язык делает их
  случайными. В AssemblyScript и C этого нет.
- **Результат не должен зависеть от числа исполнителей.** Задача видит только
  свой вход, поэтому это обычно выполняется само.

## Kernels изображений (`rakkan_image_v1`)

Нативная обработка изображений внутри изолированного воркера, capability
`image/1`. Изображения — дескрипторы в таблице хоста (целые ≥ 0).
Отрицательный результат — код ошибки:

| Код | Значение |
|---|---|
| −1 | неверный дескриптор или аргументы |
| −2 | не изображение (не PNG/JPEG) |
| −3 | превышен бюджет пикселей |
| −4 | ошибка кодирования |

| Функция | Сигнатура | Что делает |
|---|---|---|
| `decode_input` | `() -> i32` | декодирует вход задачи (PNG или JPEG) |
| `decode_blob` | `(index) -> i32` | декодирует прикреплённый блоб |
| `decode` | `(src, len) -> i32` | декодирует байты из памяти задачи |
| `create` | `(w, h) -> i32` | новое прозрачное изображение |
| `width`, `height` | `(h) -> i32` | размеры |
| `resize` | `(h, w, h) -> i32` | масштабирование в точный размер (целочисленный box-фильтр) |
| `fit` | `(h, max_w, max_h) -> i32` | вписать в рамку с сохранением пропорций |
| `crop` | `(h, x, y, w, h) -> i32` | вырезать прямоугольник |
| `grayscale` | `(h) -> i32` | оттенки серого |
| `blur` | `(h, radius) -> i32` | размытие |
| `pixels_read` | `(h, dst, len) -> i32` | скопировать пиксели RGBA8 (без премультипликации, строки сверху вниз) в память задачи |
| `pixels_write` | `(h, src, len) -> i32` | записать пиксели из памяти задачи |
| `encode_output` | `(h, format, quality) -> i32` | закодировать прямо в выход: `format` 0 — PNG, 1 — JPEG (качество 1–100); возвращает число байт |
| `free` | `(h) -> i32` | освободить |

Операции возвращают новый дескриптор, исходное изображение не меняется.
Пиксели всех изображений задачи вместе ограничены её лимитом памяти, сторона
изображения — 32 768 пикселями. Размеры проверяются до декодирования, так
что «бомба» из маленького файла не съест память. Gas: 24 за пиксель для
операций, 128 за пиксель для кодеков. Результат побайтово одинаков на любой
архитектуре.

## Kernels тензоров (`rakkan_tensor_v1`)

Матричные операции для инференса нейросетей, capability `tensor/1`. Тензор —
матрица `rows × cols` типа f32 (0), i8 (1) или i32 (2); вектор — это 1×n.
Функции возвращают дескриптор или число, отрицательное значение — ошибка:
−1 (неверные аргументы, формы или типы), −3 (превышен бюджет памяти),
−5 (блоб короче запрошенного тензора).

| Функция | Сигнатура | Что делает |
|---|---|---|
| `from_memory` | `(src, dtype, rows, cols) -> i32` | тензор из памяти задачи |
| `from_blob` | `(index, offset i64, dtype, rows, cols) -> i32` | тензор прямо из прикреплённого блоба, минуя память задачи (веса) |
| `to_memory` | `(h, dst, len) -> i32` | данные в память задачи |
| `rows`, `cols`, `dtype` | `(h) -> i32` | форма и тип |
| `matmul` | `(a, b) -> i32` | a[m,k]·b[k,n]; f32×f32→f32, i8×i8→i32 (точно) |
| `matmul_t` | `(a, b) -> i32` | a[m,k]·b[n,k]ᵀ (удобно для весов в раскладке «выход × вход») |
| `add` | `(a, b) -> i32` | поэлементно; если у b одна строка, она прибавляется к каждой строке a (bias) |
| `scale` | `(a, s f32) -> i32` | умножение на число, результат f32 (i32 деквантуется) |
| `relu` | `(a) -> i32` | max(0, x) |
| `softmax` | `(a) -> i32` | построчно, f32 |
| `quantize` | `(a, s f32) -> i32` | round(a/s) с ограничением до int8 |
| `argmax` | `(h, dst, len) -> i32` | индекс максимума каждой строки (i32) в память; возвращает число строк |
| `free` | `(h) -> i32` | освободить |

Данные little-endian, строки подряд. Результаты побитово одинаковы на любой
архитектуре и совпадают с тем же вычислением на чистом WebAssembly. Gas:
8 за умножение-сложение, 4 за элемент поэлементных операций, 40 за элемент
softmax. Kernel обычно примерно в 8 раз быстрее того же умножения на чистом
WebAssembly (`sdk/as/examples/matmul-*.ts`).

## Kernel RandomX (`rakkan_randomx_v1`)

Хеш RandomX (proof-of-work Monero) как код хоста, capability `randomx/1`.
Кэш на 256 МиБ не помещается в память задачи, поэтому его держит воркер и
пересчитывает на месте при смене ключа (около 0,6 с, в gas не входит).

| Функция | Сигнатура | Что делает |
|---|---|---|
| `hash` | `(seed, seed_len, in, in_len, out) -> i32` | 32-байтовый хеш `in` с ключом `seed`; 0 или код ошибки |
| `search` | `(seed, seed_len, blob, blob_len, nonce_off, start, count, target i64, out, out_max) -> i32` | перебирает `count` nonce от `start` (u32 LE по смещению `nonce_off`); для каждого хеша, у которого u64 LE из `hash[24:32]` меньше `target`, пишет в `out` запись из nonce (u32 LE) и хеша; возвращает число записей |

**Быстрый режим** (`rakkan_randomx_fast_v1`, capability `randomx-fast/1`): те же
функции, но с полным датасетом на 2 ГиБ, который узел держит в одном `memfd`
для всех воркеров. Режим включается флагом демона `-randomx-fast` (по умолчанию
выключен: датасет занимает 2 ГиБ памяти); узлы без него capability не объявляют.
Пока датасет строится под новый ключ (несколько секунд), `search` и `hash`
возвращают −3 («не готово»): задача должна завершиться и повторить позже.
Gas: 1,4·10⁷ за хеш.

Gas лёгкого режима: 1,6·10⁸ за хеш (≈25 мс), списывается перед каждым хешем, поэтому в
задачу с лимитом по умолчанию помещается 31 хеш. Результат не зависит от
архитектуры и наличия JIT. Пример задачи и координатор для пула Monero: проект
`rakkan-rx`.

## AssemblyScript

[AssemblyScript](https://www.assemblyscript.org) — язык, похожий на
TypeScript, который компилируется в WebAssembly. Привязки к ABI лежат в
`sdk/as` (пакет `@rakkan/as`).

**Подключение к своему проекту:**

```sh
npm install --save-dev assemblyscript@0.28.20 /путь/к/rakkan-mesh/sdk/as
```

```ts
import { input, output, log, blobs, Image, Tensor, DType } from "@rakkan/as/assembly";
```

Импортируйте именно `@rakkan/as/assembly`: голое `@rakkan/as` компилятор
AssemblyScript для пакетов со scope не находит.

**Сборка:**

```sh
npx asc task.ts --outFile task.wasm --runtime stub \
    --use abort=~lib/@rakkan/as/assembly/index/abort -O3
```

- `--use abort=…` обязателен. Иначе компилятор импортирует `abort` из `env`,
  и модуль отклоняется с `forbidden import: env.abort`. Привязки заменяют его
  своим: сообщение пишется в лог, а задача завершается ловушкой. В ошибке
  клиент увидит, например, `abort: Index out of range at ~lib/array.ts:114:42`.
- `--runtime stub` выключает сборщик мусора: задачи короткие, и память
  освобождается вместе с процессом. Поэтому не создавайте объекты в горячих
  циклах: переиспользуйте буферы (`blobs.readInto` читает в готовый буфер).
  Для долгих задач с множеством временных объектов подойдёт
  `--runtime incremental`.

Внутри репозитория примеры собирает `cd sdk/as && node build.js [имя]`.

**API привязок:**

| | |
|---|---|
| `input(): Uint8Array`, `inputString(): string` | вход задачи |
| `output(bytes)`, `outputString(s)` | дописать в выход |
| `log(message)` | строка в лог |
| `readU32(buf, off)`, `readU64(buf, off)`, `u32Bytes(v)` | little-endian помощники |
| `blobs.count()`, `blobs.size(i)` | прикреплённые блобы |
| `blobs.read(i, offset, buf): i32` | прочитать в буфер, вернуть число байт |
| `blobs.readInto(i, offset, buf, at, len): i32` | прочитать в часть буфера без новых выделений |
| `Image.decodeInput()`, `decodeBlob(i)`, `decode(bytes)`, `create(w, h)` | изображение или `null` |
| `img.width`, `img.height`, `fit`, `resize`, `crop`, `grayscale`, `blur` | операции; новое изображение или `null` |
| `img.readPixels(): Uint8Array`, `img.writePixels(px): bool` | RGBA8 для своих алгоритмов |
| `img.outputJPEG(quality)`, `img.outputPNG()`, `img.free()` | кодирование в выход |
| `Tensor.fromF32(data, rows, cols)`, `fromI8`, `fromBlob(i, offset, DType, rows, cols)` | тензоры |
| `t.matmul(b)`, `matmulT`, `add`, `scale(s)`, `relu`, `softmax`, `quantize(s)` | операции; ошибка формы прерывает задачу с сообщением |
| `t.argmax(): Int32Array`, `t.toF32(): Float32Array`, `t.free()` | результаты |

**Пример: подсчёт слова в диапазоне большого блоба** (`sdk/as/examples/wordcount.ts`,
сокращённо):

```ts
import { input, output, readU64, u32Bytes, blobs } from "@rakkan/as/assembly";

export function run(): i32 {
  const args = input();
  const offset = <i64>readU64(args, 0);   // начало диапазона
  const length = <i64>readU64(args, 8);   // длина
  const word = args.subarray(16);
  const buf = new Uint8Array(65536 + word.length);  // один буфер на всё
  // ... читать blobs.readInto(0, pos, buf, carry, n) кусками по 64 КиБ,
  //     считать вхождения, начинающиеся внутри [offset, offset+length) ...
  output(u32Bytes(count));
  return 0;
}
```

## C и другие языки

Подойдёт любой компилятор, который умеет собирать WebAssembly без WASI:
импорты из модуля `rakkan`, экспорт `run` и `memory`.

**C** (проверено с clang 21 и 22 и `wasm-ld`):

```c
// upper.c
#define RAKKAN(name) __attribute__((import_module("rakkan"), import_name(#name)))

RAKKAN(input_len) int input_len(void);
RAKKAN(input_read) int input_read(void *dst, int offset, int len);
RAKKAN(output_write) void output_write(const void *src, int len);
RAKKAN(log) void rakkan_log(const void *src, int len);

static unsigned char buf[1 << 16];

__attribute__((export_name("run"))) int run(void) {
  int n = input_len();
  if (n > (int)sizeof buf) {
    static const char msg[] = "input too long";
    rakkan_log(msg, sizeof msg - 1);
    return 1;
  }
  input_read(buf, 0, n);
  for (int i = 0; i < n; i++)
    if (buf[i] >= 'a' && buf[i] <= 'z') buf[i] -= 'a' - 'A';
  output_write(buf, n);
  return 0;
}
```

```sh
clang --target=wasm32 -O2 -nostdlib -Wl,--no-entry -o upper.wasm upper.c
```

`-nostdlib` значит, что libc нет. Если нужны `memcpy` и подобные функции,
напишите свои или соберите с минимальной libc без системных вызовов. Память
экспортируется как `memory` по умолчанию.

**Rust** (цель `wasm32-unknown-unknown`; в этом репозитории не
проверялся):

```rust
#[link(wasm_import_module = "rakkan")]
extern "C" {
    fn input_len() -> i32;
    fn input_read(dst: *mut u8, offset: i32, len: i32) -> i32;
    fn output_write(src: *const u8, len: i32);
}

#[no_mangle]
pub extern "C" fn run() -> i32 {
    let n = unsafe { input_len() } as usize;
    let mut buf = vec![0u8; n];
    unsafe { input_read(buf.as_mut_ptr(), 0, n as i32) };
    buf.make_ascii_uppercase();
    unsafe { output_write(buf.as_ptr(), n as i32) };
    0
}
```

```sh
cargo build --release --target wasm32-unknown-unknown   # crate-type = ["cdylib"]
```

Проверьте готовый модуль командой `rakkan-node run`: если компилятор
добавил запрещённые импорты (например, `env` или `wasi_snapshot_preview1`),
модуль будет отклонён с `forbidden_import` и именем импорта.

## Отладка

**Локальный запуск** в той же песочнице, что на узлах, без сети:

```sh
rakkan-node run -input data.bin -gas 1000000000 -mem 64 -timeout 5s task.wasm
```

| Флаг | Смысл |
|---|---|
| `-input файл` или `-input -` | вход из файла или stdin |
| `-entry имя` | другая точка входа |
| `-gas`, `-mem` (МиБ), `-timeout` | лимиты (локально потолков нет) |
| `-isolation strict\|ns\|process\|none` | изоляция воркера; `none` запускает в самом процессе |

Выход задачи идёт в stdout, лог в stderr, затем строка
`exit=… gas=… elapsed=…`. Код выхода команды: 0 при успехе, 3 при ненулевом
коде выхода задачи, 1 при ошибке (её текст в stderr). Прикреплённые блобы
локально не подключаются: такие задачи проверяйте на узле.

**Удалённо:**
- `log()` — главный инструмент: лог приходит и в результате, и в ошибке;
- `gasUsed` в результате подскажет, сколько осталось до бюджета;
- для ловушек AssemblyScript текст `abort` с файлом и строкой приходит в
  сообщении ошибки.
