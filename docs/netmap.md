# Карта сети

`rakkan-node map` строит карту сетей, в которых работают участники mesh: устройства,
сети, связи, местоположение. Каждый участник собирает наблюдения о своих сетях
и видит **только свою** карту. **Всю карту сети видит лишь владелец корневого
ключа** (`root.key`): участники отправляют ему наблюдения запечатанными так, что
прочитать их без корневого ключа нельзя ни ретрансляторам, ни другим
участникам, ни узлам, где они лежат.

Это подкоманда самого узла: отдельной программы нет, нужен только `rakkan-node` (Linux; на других системах команда сообщает, что не поддерживается).

## Кто что видит

```
участник A      rakkan-node map scan/watch → своё хранилище (map.db) → serve: карта A
                rakkan-node map publish ──► rakkan-node A: запечатывает на ключ корня
                                         │  gossip + спул на диске (30 дней / 64 МиБ)
                                         ▼
                                  все участники: носят отчёты, прочитать не могут
                                         │
владелец корня  rakkan-node map collect --root-key root.key  (с любого узла сети)
                  → network.db → rakkan-node map serve --db …/network.db: карта всей сети
```

- Адрес сети — это peer ID корневого ключа, публичный ключ в нём. По нему любой
  участник запечатывает отчёт (эфемерный X25519 + AES-256-GCM, `internal/sealed`),
  а открыть его может только тот, у кого корневой закрытый ключ.
- Узел подписывает отчёт своим сертификатом. Ретрансляторы проверяют сертификат
  и подпись, не открывая содержимое; на автора действует лимит 60 отчётов в минуту.
- **Гость** открытой сети (без сертификата, с доказательством работы) тоже отправляет
  отчёты: вместо сертификата в пакете его ключ и доказательство, ретрансляторы
  проверяют их по действующей политике, лимит — 4 отчёта в минуту. Корень принимает
  такой отчёт, но видит в нём слово гостя, а не участника (см. «Гости» ниже).
- Корневой ключ читает только `collect`, и только в запускаемой вами команде; демону он не нужен.
  Администраторы (`admin`) карту сети не видят: у них нет корневого ключа.
- Узел-участник (`rakkan-node`) про карту ничего не знает: он принимает
  непрозрачный отчёт по `POST /v1/reports` и отдаёт запечатанные пакеты по
  `GET /v1/reports`, как и любое приложение поверх локального API
  ([docs/dev/http-api.md](dev/http-api.md#отчёты-для-корня)).

## Участник

```sh
rakkan-node map scan                 # или watch; карта остаётся вашей
rakkan-node map serve                # посмотреть свою карту: http://127.0.0.1:8742
rakkan-node map publish              # отправить новое корню (один раз)
rakkan-node map publish --every 15m  # и дальше повторять (демон делает это сам: см. ниже)
rakkan-node map publish --location drop --wan drop   # не отправлять координаты и внешние адреса
```

`publish` отправляет только **ваши** наблюдения и только те, что ещё не уходили
(признак «отправлено» хранится в самой базе; `--all` отправит всё заново). Уходит всё, что вы наблюдали: адреса, имена
устройств, координаты. Корень их увидит. Оставить часть себе можно флагами
`--location drop|coarse:1km` и `--wan drop`. Нужны запущенный `rakkan-node`
с сертификатом участника или гостевым доказательством работы и его сокет: ищется там,
куда кладут установщики, или `--api`/`--config`, как у `rakkan-web`.

## Автоматически, из демона

Каждый узел с сертификатом сам строит карту своих сетей и отправляет её корню:
раз в 15 минут (с разбросом ±10%, чтобы узлы не отправляли одновременно) он
отправляет новые наблюдения запечатанными и удаляет старые. Собирает он **пассивно**:
слушает анонсы mDNS и SSDP, читает таблицу соседей ядра и кеш Wi-Fi, а при наличии
прав на сырой захват разбирает ARP, DHCP и LLDP (как `map watch`; без прав остальное
работает). Ни одной пробы в сеть при этом не уходит; собранное сохраняется раз в
минуту. Ничего запускать не нужно. Флаги демона (они же поля JSON-конфига):

| флаг | по умолчанию | смысл |
|---|---|---|
| `-map-every` | `15m` | период; `0` выключает карту совсем |
| `-map-scan` | `false` | дополнительно сканировать свои сети **активно** перед каждой отправкой: ping-sweep подсети (или её /24, если подсеть больше 1024 адресов), запросы mDNS и SSDP, TCP-пробы нескольких портов. Включает только владелец узла, флагом на самом узле; корень и сеть включить его не могут |
| `-map-keep` | `168h` | сколько хранить наблюдения; всё старше удаляется |
| `-map-dir` | `<data>/map` | где лежат `map.db` и `observer.key` узла (не в домашнем каталоге: у службы его может не быть) |
| `-map-location`, `-map-wan` | `keep` | не отправлять координаты и внешние адреса: `drop`, `coarse:1km` |

**Активное сканирование выключено по умолчанию**: узел только слушает. Пассивная
карта беднее: видны устройства, которые сами заговорили или уже есть в таблице
соседей, а тихие хосты нет, и без прав на сырой захват ещё меньше. Чтобы узел
сканировал активно, владелец запускает демон с `-map-scan` (там, где ему это
разрешено). Всю отправку отключает `-map-every 0`. Гость отправляет карту так же,
как участник. Узел с `-reports off` и узлы не на Linux не отправляют ничего и ничего
не сообщают об этом, кроме отладочного лога. Явно заданный `-map-every` при этих условиях — ошибка запуска.

Карту такого узла смотрят так: `rakkan-node map serve --db <data>/map/map.db`
(или вкладка «Карта» в `rakkan-web -map-db <data>/map/map.db`).

### Узел не растёт со временем

- Хранилище узла чистится после каждого раунда: наблюдения старше `-map-keep`
  удаляются (кроме своих, ещё не отправленных), файл сжимается (`VACUUM`), журнал
  SQLite усекается.
- Раунд читает только то, что ещё не отправлено (признак в самой базе), порциями по
  2000, а не всё хранилище.
- Между раундами ничего не держится: хранилище открывается на раунд и
  закрывается, память скана возвращается системе (`debug.FreeOSMemory`).
- Спул отчётов ограничен (64 МиБ, 4096 пакетов, 30 дней: что наступит раньше. В сети из N участников с периодом 15 минут 4096 пакетов — это примерно 43/N часов, так что при большой сети корень должен забирать отчёты чаще, а `rakkan-web -root-key` делает это раз в минуту), список отправителей для
  лимита частоты подчищается.
- Просмотр читает окно (`-map-keep`), не больше 200 000 наблюдений.

Один раунд на подсеть с сотней устройств даёт сотни наблюдений, при 15 минутах и
семи днях это десятки тысяч записей на участника. Если сеть большая, увеличьте
период или сократите `-map-keep`.

## Владелец корня

```sh
rakkan-node map collect --root-key root.key           # забрать и открыть всё, что накопилось
rakkan-node map collect --root-key root.key --every 10m
rakkan-node map serve --db ~/.local/share/rakkan/network.db   # карта всей сети
rakkan-node map show  --db ~/.local/share/rakkan/network.db
```

Периодически то же делает `rakkan-web` (ниже). `collect` читает спул любого узла сети: отчёты, которых у этого узла ещё нет,
он подтянет у других участников за пару минут (узлы сверяют спулы между собой
каждые 30 с). Спул хранит отчёты 30 дней, так что собирать нужно не реже. Что `collect` делает с каждым пакетом:
проверяет сертификат автора (`--crl crl.json` — ещё и отзыв), открывает корневым
ключом, проверяет подписи наблюдений и добавляет их в `network.db` (повторы
безвредны). Ключи наблюдателей, пришедшие из отчётов, получают в `network.db`
доверие `trusted` и имя автора, если вы не решили иначе (`rakkan-node map trust set …`).
Курсор чтения хранится рядом (`network.db.cursor`) по каждому узлу отдельно.

`rakkan-node` держит спул отчётов в `<data>/reports`; флаги `-reports DIR|off`
и `-reports-mb`. Отчёты сети может увидеть только корень, но кто и когда
отправил отчёт, видно участникам (автор отчёта подписан сертификатом).

## Карта в rakkan-web

На странице узла есть вкладка «Карта»: граф и географическая карта, поиск,
фильтры, ползунок «на момент» (тот же просмотрщик, что у `map serve`).

```sh
rakkan-web                                   # ваша собственная карта (~/.local/share/rakkan/map.db)
rakkan-web -map-db <data>/map/map.db         # карта, которую строит демон этого узла
rakkan-web -root-key root.key                # ВСЯ сеть: только у владельца корневого ключа
```

С `-root-key` `rakkan-web` сам раз в минуту (`-map-collect`) забирает отчёты у
узла, открывает их ключом и показывает `network.db`; ключ читается в этом процессе
и нигде больше не используется. Без ключа показать больше своей карты нечем: чужие
отчёты запечатаны. Данные карты лежат под `/app/map/`, как и остальное API
страницы, и требуют токен, когда страница слушает не только localhost (страница
`/map/` открыта, как главная, и берёт токен, который вы ввели на главной).
Подложка карты не грузится (`-map-tiles` включает свою или OpenStreetMap, тогда
сервер тайлов узнаёт, какой район вы смотрите).

## Что это не защищает

- Корень доверяет сертификатам: участник, чей ключ украден, может присылать ложные
  наблюдения, пока его сертификат не отозван. Отзыв — как обычно (`network revoke`).
- Утечка корневого ключа открывает все отчёты, которые кто-то сохранил. Прямой
  секретности нет: ключ корня и без того главный секрет сети.
- Размер и время отчёта видны всем, кто его переносит.
- Файлы `.rkm`, которые вы экспортируете сами (`export -o`), уходят туда, куда вы
  их отправите: это вне канала отчётов.
- Сертификат автора проверяется при `collect`: отчёт участника, чей сертификат
  успел истечь, `collect` отвергнет. Собирайте чаще срока сертификатов.

# Как собирается карта

Ниже — описание самого сборщика, перенесённого из отдельного проекта rakkan-map
без изменений в работе. Формат наблюдений — [netmap-spec/format.md](netmap-spec/format.md).

## Два режима сбора

```sh
rakkan-node map scan                 # активный: ping-sweep, mDNS/SSDP-запросы, TCP-пробы, SSH host keys
rakkan-node map watch                # пассивный: только слушает, ничего не отправляет
```

Оба пишут в одно рабочее хранилище (`~/.local/share/rakkan/map.db`) и
подписывают наблюдения ключом наблюдателя (`~/.config/rakkan/observer.key`).
В наблюдении записан режим (`active` / `passive` / `local`), но на слияние он не влияет.

Без прав работают mDNS, SSDP и таблица соседей ядра. Чтобы пассивный режим
видел ещё ARP, DHCP (hostname, vendor class), NDP и LLDP (свитч и порт),
нужен `CAP_NET_RAW`:

```sh
sudo setcap cap_net_raw=ep ./rakkan-node
```

Активный режим сканирует свою подсеть, а если она больше `--max-hosts`
(1024), то только свою /24. Диапазон можно задать явно через `--cidr`.
**Активно сканируйте только сети, на которые у вас есть разрешение.**

## Wi-Fi

`scan` и `watch` записывают точки доступа в радиусе — тот же список, что
показывает меню Wi-Fi: SSID, BSSID, диапазон, канал, тип защиты, уровень сигнала.
`scan` просит NetworkManager о свежем скане (как открытие меню Wi-Fi), `watch`
только читает кэш, который ОС собирает сама. Точка доступа, к которой вы
подключены, входит в вашу сеть и связана с интерфейсом. Клиентские устройства
чужих сетей не собираются. `--no-wifi` отключает Wi-Fi в `scan`.

## Проводная и L3-топология

```sh
# опрос своих коммутаторов/роутеров (только явно указанные, только со своими учётными данными)
RAKKAN_SNMP_COMMUNITY=... rakkan-node map scan --no-discover --snmp 192.168.1.2,192.168.1.3
# SNMPv3: --snmp-v3-user USER, пароли — в RAKKAN_SNMP_V3_AUTH / RAKKAN_SNMP_V3_PRIV (SHA/AES)

# L3-путь до целей (без root, как tracepath)
rakkan-node map scan --no-discover --trace 1.1.1.1,9.9.9.9
```

SNMP даёт: какой MAC за каким портом (FDB), соседей по LLDP с портами с обеих
сторон, ARP-таблицы роутеров (включая чужие VLAN), `sysLocation` (задел для
фазы 5). Порт со многими MAC или с LLDP-соседом считается аплинком: хосты за
ним получают связь `l2-behind`, а не `l2`. Коммутатор, опрошенный по SNMP, и он же,
услышанный пассивным LLDP-сниффером, — одно устройство (общий `lldp:`-идентификатор).

Хопы traceroute с публичными адресами глобальны (`gip:`): пути от наблюдателей
из разных сетей склеиваются на общих роутерах.

## Местоположение

Положение — такие же подписанные утверждения, как остальное; уровень
(`unknown` → `region` → `area` → `precise`) выводится из радиуса погрешности.

```sh
rakkan-node map locate here --lat 50.087 --lon 14.42 --radius 20 --logical "Lab / desk 3"  # где наблюдатель
rakkan-node map locate gps                                   # одна отметка из запущенного gpsd
rakkan-node map locate set d3ocaau --lat ... --lon ... --radius 5   # где устройство (id из show) или mac:..., bssid:...
rakkan-node map locate list
rakkan-node map export --geojson > map.geojson
```

Несколько независимых оценок усиливают друг друга (радиус сжимается), противоречащие
помечаются `!`. Известная позиция переходит по кабелю (`l2`), радио (`wifi`) и «где-то за
портом» (`l2-behind`) с ростом радиуса и падением уверенности (`~` в таблице — «выведено,
а не наблюдалось»). Через маршрутизаторы и просто по общей сети положение **не** переходит.
GPS-отметка наблюдателя устаревает за часы, ручная метка стационарного устройства — за год.
`sysLocation` коммутаторов читается как логическое место. Подробности — `spec/format.md` §9.

**Положение чувствительно и уезжает вместе с картой** при `export`; фильтры
приватности — `--location` и `--wan` у `export` и `publish`.

## Тип устройства

Каждому устройству резолвер приписывает тип с уверенностью и причинами (spec §12):
стационарный компьютер, ноутбук, сервер, телефон, планшет, телевизор и медиа,
интернет вещей, принтер, сетевое оборудование. Если признаков хватает только на
группу, тип будет «компьютер» или «телефон/планшет». Признаки: модели (включая
идентификаторы Apple), имена, mDNS-сервисы, UPnP-типы, DHCP vendor class, порты,
sysDescr, роли. Тип вычисляется заново при каждом просмотре и в карту не пишется.
Наблюдатель сам сообщает тип своего корпуса из SMBIOS.

```sh
rakkan-node map class                      # все устройства: тип, уверенность, почему
rakkan-node map class d47zbpd tv           # указать тип вручную: он главнее вывода
```

В `rakkan-node map show` тип выводится в колонке TYPE (`?` — уверенность ниже 60 %), в
`rakkan-node map show ID` — с причинами. В веб-интерфейсе узлы раскрашены по типу, есть
фильтр по типу.

## Просмотр

```sh
rakkan-node map show                 # сводка по сетям
rakkan-node map show d3ocaau         # всё об устройстве и почему его идентификаторы склеены
rakkan-node map show --json
rakkan-node map export --dot | dot -Tsvg > map.svg
```

## Веб-интерфейс

```sh
rakkan-node map serve                       # http://127.0.0.1:8742
rakkan-node map serve --from a.rkm,b.rkm    # смотреть файлы, не трогая хранилище
rakkan-node map serve --tiles off           # без подложки карты: ни одного запроса наружу
```

Граф (сети, устройства, связи по видам) и географическая карта (точки с кругами
погрешности; пунктир — положение выведено по связям). Поиск, фильтры по сети, режиму
наблюдения, видам связей, типу устройства; ползунок «на момент» показывает карту такой, какой она была
известна тогда. Пока ползунок на «сейчас», страница подхватывает то, что дописывает
запущенный `rakkan-node map watch`. Клик по устройству — всё о нём: положение и его источники,
связи, идентификаторы, утверждения, почему идентификаторы склеены.

### Поиск

Без ключей слова ищутся по всем фактам об устройстве и по соседним: его сети
(префикс, SSID, шлюз), AS, порты на связях. Совпасть должны все слова. Ключи сужают
поиск:

| запрос | что найдёт |
|--------|------------|
| `type:laptop`, `тип:телефон`, `type:computer` | по типу; группа включает листья |
| `port:22`, `port:tcp/443` | открытый порт или порт объявленного сервиса |
| `service:ipp`, `ip:10.82.0.0/16`, `mac:00:11:32` | сервис, адрес или подсеть, MAC |
| `name:`, `vendor:`, `model:`, `os:`, `role:`, `ssid:`, `net:`, `as:` | соответствующие факты |
| `seen:<1h`, `seen:>7d` | видели за последний час / давно |
| `observer:1dd0`, `mode:passive`, `method:lldp`, `loc:area`, `id:`, `has:model` | кто и как видел, место, наличие факта |
| `near:type:network`, `near:10.82.0.1` | связанные с подходящим устройством |
| `dhcp.vendor:android` | любое утверждение по его ключу |
| `port:22,80`, `mac:=…`, `-type:tv`, `name:"living room"` | любое из значений, точно, исключить, фраза |

`Tab` дополняет ключ, `/` ставит курсор в поиск, `?` рядом с полем открывает справку.

Всё нужное вшито в бинарник (Cytoscape.js 3.30.2, Leaflet 1.9.4 —
`internal/web/static/vendor/VENDOR.md`). Наружу ходит только подложка карты (тайлы
OpenStreetMap): тайл-сервер узнаёт, какую область вы смотрите; `--tiles off` или свой
сервер тайлов через `--tiles URL`.

Сервер слушает только `127.0.0.1` и отвечает только на запросы с `Host` этой машины —
иначе любая открытая в браузере страница могла бы прочитать карту через DNS rebinding.
Строки из карт (в том числе чужих) выводятся только как текст. Чтобы открыть доступ
из сети: `--addr 0.0.0.0:8742 --allow-host имя-машины` — но помните, что карта содержит
адреса и координаты.

## Интернет-уровень

Карты из разных сетей и городов соединяются на публичных адресах: выходах сетей в
интернет и общих роутерах на трассах. Ничего не сканируется.

```sh
rakkan-node map scan                          # спросит у шлюза внешний адрес (NAT-PMP / UPnP IGD), --no-wan — не спрашивать
rakkan-node map scan --stun stun.example:3478 # плюс адрес, видимый из интернета (внешний сервер — только по флагу)
rakkan-node map scan --no-discover --trace 9.9.9.9
rakkan-node map asn import ip2asn-combined.tsv.gz   # справочник IP→AS (https://iptoasn.com, общественное достояние)
rakkan-node map show                          # раздел «internet»: AS, сети, которые в них выходят, роутеры
```

Справочник AS локален и в карты не попадает: это то, как маршрутизируется адрес сегодня,
а не то, что кто-то видел. В веб-интерфейсе AS — отдельные узлы. Внешний адрес сети —
чувствительные данные: `export`/`publish` с `--wan drop` его не передают.

`rakkan-node map verify` без файлов проверяет подписи всего хранилища (при загрузке они не
перепроверяются — так в 10 раз быстрее; при импорте и синхронизации проверяется всё).

## Доверие к ключам наблюдателей

Чужие карты (импортированные файлы) нельзя принимать на веру: кто угодно может подписать ложное наблюдение.
Книга доверия — локальная, в карты не попадает:

```sh
rakkan-node map key                                   # свой ключ — передайте его тем, с кем обмениваетесь
rakkan-node map trust set <ключ> trusted --name ноут  # доверять (полный вес)
rakkan-node map trust set <ключ> blocked              # игнорировать и не передавать дальше
rakkan-node map trust list
```

Утверждения неизвестных ключей весят вдвое меньше, и неизвестный ключ не может склеить
устройства вопреки доверенным данным (нельзя «приклеить» чужой MAC к своему SSH-ключу).

### Гости: сверка и доверие

Сертификат — поручительство корня за участника; гость поручился только работой. Поэтому
`collect` помечает ключи наблюдателей, пришедшие через гостя, как «гостевые» (уровень
`unknown` и признак `guest` в книге доверия), а карта сверяет их с доверенными:

- Вес гостя начинается с 0.25 (у неизвестного ключа 0.5, у доверенного 1). Каждый
  различный факт гостя, который подтвердили доверенные наблюдатели (то же имя хоста,
  производитель, ОС для того же устройства), поднимает вес; 10 подтверждённых фактов
  доводят его до 0.5. Выше гость не поднимется: доверенным ключ делает только ваша книга.
- Факт, которого доверенные не называли при том, что про это устройство и этот признак
  они что-то сообщили, — расхождение. То же — попытка гостя склеить устройства вопреки
  доверенным данным. Вес падает пропорционально доле расхождений в квадрате.
- Если проверено не меньше 3 фактов и половина из них расходится, наблюдатель
  «оспорен» и в карту не попадает совсем (в `map trust list` — `DISPUTED`). Данные не
  удаляются: решение пересматривается при каждой сборке карты.
- Повторы одного факта при каждом скане считаются один раз. Если доверенные сами
  меняли значение со временем, подтверждённым считается любое из названных ими.
- Ваше решение сильнее сверки: `map trust set <ключ> trusted` (или `blocked`) снимает
  гостевую метку. Если тот же ключ позже пришёл в отчёте участника, он становится доверенным.

Сверка видит только то, о чём сообщили и доверенные: устройства, которых видит один гость,
проверить нечем, и они остаются на карте с весом гостя. Гость может завести новый ключ
наблюдателя, чтобы сбросить плохую историю, но начнёт с минимального веса и без подтверждений.

Ротация ключа: `rakkan-node map key rotate` — старый ключ объявляет преемника, доверие переходит;
При утечке: `rakkan-node map key rotate --compromised-since 36h` — подписи ключа с того момента
недействительны везде, куда дойдёт отзыв; новому ключу доверяют явно.

## Обмен и слияние

```sh
rakkan-node map export -o mine.rkm               # своё хранилище → портативный файл
rakkan-node map import theirs.rkm                # чужую карту → в своё хранилище
rakkan-node map merge -o all.rkm a.rkm b.rkm     # слить файлы без хранилища
rakkan-node map verify all.rkm                   # подписи + digest набора
rakkan-node map show --from a.rkm,b.rkm          # посмотреть объединение, ничего не сохраняя
```

Слияние коммутативно, ассоциативно и идемпотентно: одинаковый набор
наблюдений даёт одинаковый `set digest` при любом порядке слияний.
