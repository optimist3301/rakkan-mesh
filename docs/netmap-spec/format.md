# rakkan map format — v1

Статус: черновик, фаза 0. Версия схемы наблюдения: `1`. Версия контейнера: `1`.

## 1. Принцип

Карта — это **множество неизменяемых подписанных наблюдений**. Граф (устройства,
сети, связи, местоположения) не хранится, а *вычисляется* из наблюдений
детерминированными правилами (см. §6).

Слияние карт = объединение множеств наблюдений. Это G-Set CRDT:

- коммутативно: `merge(A, B) == merge(B, A)`
- ассоциативно: `merge(A, merge(B, C)) == merge(merge(A, B), C)`
- идемпотентно: `merge(A, A) == A`

Наблюдения из **активного** сканирования, **пассивного** наблюдения и **локальной
интроспекции** имеют одинаковый формат и отличаются только полем `mode`, поэтому
сливаются без всяких особых правил. Режим влияет лишь на интерпретацию (вес
доказательства, подсказки в UI), но никогда — на возможность слияния.

## 2. Наблюдение

### 2.1 Тело (`Body`)

CBOR map с целочисленными ключами:

| key | имя       | тип          | обяз. | смысл |
|-----|-----------|--------------|-------|-------|
| 0   | v         | uint         | да    | версия схемы, `1` |
| 1   | observer  | bstr(32)     | да    | Ed25519 публичный ключ наблюдателя |
| 2   | time      | int          | да    | начало наблюдения, Unix ms (UTC) |
| 3   | until     | int          | нет   | конец интервала (агрегированные пассивные наблюдения) |
| 4   | count     | uint         | нет   | сколько раз событие видели в интервале |
| 5   | mode      | uint         | да    | 1 = active, 2 = passive, 3 = local |
| 6   | method    | tstr         | да    | метод сбора, см. §5 |
| 7   | vantage   | map          | нет   | точка наблюдения, см. §2.2 |
| 8   | subject   | [tstr]       | да    | идентификаторы, отн. к **одной** сущности, см. §3 |
| 9   | claims    | [Claim]      | нет   | утверждения о сущности |

`Claim` — CBOR map: `{1: key tstr, 2: value tstr, 3: confidence uint}`.
`confidence` — промилле (0..1000); отсутствие ключа 3 означает 1000.
Значения всегда строки (числа — десятичной записью), что исключает
неоднозначность канонизации чисел и float.

### 2.2 Vantage

`{1: iface tstr, 2: iface_mac tstr, 3: net tstr, 4: addr tstr}` — все поля
необязательны. `net` — идентификатор сети (§4), в которой сделано наблюдение.

### 2.3 Канонизация

Перед кодированием:

1. `subject` — отсортировать лексикографически по байтам, удалить дубликаты; не пуст.
2. `claims` — отсортировать по `(key, value, confidence)`, удалить точные дубликаты.
3. Пустые необязательные поля опускаются.
4. Кодирование — Core Deterministic Encoding (RFC 8949 §4.2.1): кратчайшие
   длины, ключи map отсортированы, никаких indefinite-length.

Читатель обязан проверить, что декодирование и повторное кодирование тела
дают те же байты (для `v == 1`). Иначе одно и то же содержимое могло бы
иметь разные id, и слияние перестало бы быть идемпотентным.
Тела с `v > 1` читатель сохраняет как есть (байты неприкосновенны), не проверяя
каноничность, — это обеспечивает прямую совместимость.

### 2.4 Идентификатор и подпись

```
id  = BLAKE3-256( "rakkan-obs-v1\x00" || body_bytes )
sig = Ed25519.Sign( observer_priv, "rakkan-sig-v1\x00" || id )
```

Время входит в тело, поэтому повторное наблюдение того же факта в другой момент —
другое наблюдение. Это правильно: мы храним историю, а не состояние.

### 2.5 Запись

Запись наблюдения в потоке — CBOR array `[body_bytes bstr, sig bstr]`.
`id` в файле не хранится — он всегда пересчитывается.

## 3. Идентификаторы

Формат: `kind:value` либо, для идентификаторов, имеющих смысл только внутри
сети, `kind:<netid>/value`. Все MAC — нижний регистр, `aa:bb:cc:dd:ee:ff`.

| kind    | пример                         | сила    | пояснение |
|---------|--------------------------------|---------|-----------|
| `rkm`   | `rkm:<hex pubkey>`             | strong  | устройство, на котором работает наблюдатель |
| `ssh`   | `ssh:SHA256:abc…`              | strong  | отпечаток SSH host key |
| `uuid`  | `uuid:2fac1234-…`              | strong  | UPnP/SSDP UUID |
| `lldp`  | `lldp:mac/00:11:…`             | strong  | LLDP chassis id (подтип/значение) |
| `mac`   | `mac:00:11:22:33:44:55`        | strong  | глобально уникальный MAC (бит U/L = 0) |
| `bssid` | `bssid:00:11:22:33:44:56`      | strong  | радиоинтерфейс точки доступа Wi-Fi (у одной точки их может быть несколько) |
| `lmac`  | `lmac:<net>/02:11:…`           | medium  | локально администрируемый (рандомный) или виртуальный (VRRP/HSRP) MAC — уникален только в сети |
| `host`  | `host:<net>/nas`               | medium  | имя хоста (DHCP option 12, rDNS) |
| `mdns`  | `mdns:<net>/printer.local`     | medium  | mDNS-имя |
| `ip`    | `ip:<net>/192.168.1.10`        | weak    | IP-адрес в подключённой сети; связь с устройством ограничена во времени |
| `rip`   | `rip:<net>/10.20.0.1`          | weak    | приватный адрес вне подключённых сетей (хоп маршрута, другой VLAN), как он виден из сети `<net>` |
| `gip`   | `gip:80.80.80.1`               | weak    | публичный адрес; глобален — на нём сходятся пути из разных сетей |
| `net`   | `net:<netid>`                  | —       | сама сеть как сущность |

Перечень расширяемый: неизвестный kind читатель трактует как `medium`.

`ip`, `rip` и `gip` — **адресные** идентификаторы: их связь с устройством
действует только во времени (§6.2). Публичным считается глобальный unicast,
кроме приватных, CGNAT (100.64/10), 192.0.0.0/24, 198.18/15 и документационных
диапазонов — такие адреса получают `rip`.

Семантика `subject`: наблюдатель утверждает, что *в момент `time`* все перечисленные
идентификаторы относились к одной сущности. Всё в `claims` относится к ней же.

## 4. Идентификатор сети

IP-адрес бессмыслен без контекста: `192.168.1.1` существует в миллионах сетей.
Каждая L2-сеть получает `netid`, который **независимые наблюдатели вычисляют
одинаково**:

```
netid = "n" + base32lower_nopad( BLAKE3-256( "rakkan-net-v1\x00" || gw_mac || "|" || ipv4_prefix )[:10] )
```

где `gw_mac` — MAC шлюза по умолчанию (нижний регистр), `ipv4_prefix` —
каноническая запись сети, например `192.168.1.0/24`.

Если MAC шлюза — виртуальный адрес резервирования (VRRP `00:00:5e:00:01/02:xx`,
HSRP `00:00:0c:07:ac:xx` и `00:00:0c:9f:fx:xx`, GLBP `00:07:b4:00:…`), он описывает
группу резервирования, а не сеть: меняется при переключении роутеров и одинаков в
бесчисленных несвязанных сетях. Тогда вместо MAC берётся IP шлюза:

```
netid = "n" + base32lower_nopad( BLAKE3-256( "rakkan-vnet-v1\x00" || gw_ip || "|" || ipv4_prefix )[:10] )
```

Отдельный домен хэширования исключает совпадение с идентификаторами по MAC. Для сетей
с обычным MAC шлюза значение не изменилось.

Если MAC шлюза узнать нельзя, используется локальная область, которая
намеренно **не** совпадёт ни у какого другого наблюдателя (консервативно: лучше
не склеить, чем склеить ошибочно):

```
netid = "x" + base32lower_nopad( BLAKE3-256( "rakkan-lnet-v1\x00" || observer_pub || iface || "|" || prefix )[:10] )
```

## 5. Методы (`method`) и режимы

| method        | mode    | что даёт |
|---------------|---------|----------|
| `self`        | local   | собственное устройство, интерфейсы, hostname |
| `route`       | local   | сеть, шлюз |
| `neigh`       | local / passive / active | ARP/NDP-кэш ядра: пары MAC↔IP |
| `ping`        | active  | живость хоста, TTL |
| `mdns`        | active / passive | mDNS имена, сервисы, TXT |
| `ssdp`        | active / passive | UPnP устройства, UUID, тип |
| `upnp-desc`   | active  | описание устройства UPnP (модель, производитель) |
| `rdns`        | active  | PTR-имена |
| `tcp`         | active  | открытые порты, баннеры |
| `ssh-hostkey` | active  | отпечаток SSH host key |
| `arp`         | passive | ARP-пакеты из эфира |
| `dhcp`        | passive | DHCP: hostname, vendor class, fingerprint |
| `ndp`         | passive | IPv6 Neighbor Discovery |
| `lldp`        | passive | соседство по проводу: свитч, порт |
| `wifi-scan`   | passive / active | точки доступа в радиусе из кэша сканирования ОС (passive) или после запроса свежего скана (active) |
| `wifi-assoc`  | local   | точка доступа, к которой подключён наблюдатель; SSID сети |
| `snmp`        | active  | опрос явно указанных устройств: system, IF-MIB, BRIDGE/Q-BRIDGE FDB, LLDP-MIB, ARP |
| `trace`       | active  | L3-путь до явно указанных целей (UDP + IP_RECVERR, без привилегий) |

Режим отражает, кто вызвал появление данных:
- `active` — мы послали пакеты, чтобы узнать это;
- `passive` — мы только слушали чужой трафик;
- `local` — мы прочитали состояние собственной системы.

Уровень сигнала (`rssi.dbm`) — утверждение о паре «наблюдатель ↔ передатчик»,
округлённое вниз до 3 дБ, чтобы обычный разброс измерений стационарного
наблюдателя схлопывался агрегацией. Точное значение здесь не нужно: это сырьё
для оценки местоположения, где важны показания разных наблюдателей.

Пассивные наблюдения агрегируются: одинаковые события (тот же метод, vantage,
subject, claims) за окно записываются одним наблюдением с `time`, `until`, `count`.

## 6. Построение графа (resolve)

Ниже — нормативное описание v1 правил. Правила могут улучшаться без изменения
формата: граф просто пересчитывается.

1. **Кластеры.** Union-find по идентификаторам. Для каждого наблюдения
   объединяются все не-`ip` идентификаторы его `subject`.
   - `strong` и `lmac` объединяются безусловно.
   - `medium` (`host`, `mdns`, неизвестные) объединяются во втором проходе и
     только если это не сливает два кластера, содержащие разные значения одного
     и того же strong-kind, кроме `mac` (у устройства бывает несколько MAC, но
     не два разных `rkm`). Отказ записывается как конфликт.
   - Блок-лист значений `host`/`mdns`: `localhost`, `localhost.localdomain`, пустые.
2. **IP-привязки.** Пара (адресный идентификатор, кластер) из одного наблюдения — привязка с
   временем. Наблюдение, в `subject` которого только адресные идентификаторы, присоединяется к кластеру,
   у которого есть привязка к этому `ip` с ближайшим временем в окне ±24 ч.
   Иначе создаётся устройство «только IP».
3. **Сети.** `net:<id>` — отдельные сущности. Устройство принадлежит сети, если
   какой-либо его scoped-идентификатор содержит этот netid или его видели из
   vantage этой сети L2-методом (`neigh`, `arp`, `dhcp`, `ndp`, `lldp`).
4. **Утверждения.** Для каждого ключа claim собираются все значения с максимальной
   уверенностью, first/last seen, числом наблюдений, множеством наблюдателей и
   режимов. «Лучшее» значение: max confidence, затем последнее по времени.
5. **Связи.** Claim с ключом `link.<kind>` и значением-идентификатором задаёт связь
   между сущностью наблюдения и сущностью этого идентификатора:

   | kind         | смысл |
   |--------------|-------|
   | `l2`         | прямое проводное соседство (LLDP, порт FDB с единственным хостом) |
   | `l2-behind`  | сущность где-то за этим портом (порт-аплинк или порт со многими MAC) |
   | `wifi`       | подключение интерфейса наблюдателя к точке доступа |
   | `l3`         | соседние отвечающие хопы маршрута; при пропуске молчащих хопов — `trace.gap` и пониженная уверенность |

   Порты: `link.port.a` — на стороне сущности наблюдения, `link.port.b` — на стороне
   идентификатора-значения. Членство в сети дают только on-link идентификаторы;
   `rip` его не дают — адрес виден *из* сети, а не находится *в* ней.
6. **ID устройства** — `d` + base32(BLAKE3(минимальный по силе-затем-лексикографически
   идентификатор кластера))[:10]. Стабилен при добавлении новых наблюдений, пока
   кластер не получает более сильный идентификатор.

## 7. Контейнер `.rkm`

```
magic   = 89 52 4B 4D 0D 0A 1A 0A          ("\x89RKM\r\n\x1a\n")
payload = zstd( CBOR sequence )
```

Последовательность CBOR (RFC 8742):

1. Header — map `{1: container_version=1, 2: created_ms, 3: producer tstr}`
2. N записей — arrays (§2.5), отсортированы по `id` (для детерминированных файлов)
3. Trailer — map `{1: count uint, 2: set_digest bstr(32)}`

`set_digest = BLAKE3-256( "rakkan-set-v1\x00" || id_1 || … || id_N )` по
отсортированным id. Две карты с одинаковым набором наблюдений имеют одинаковый
digest независимо от истории слияний. Полноценное дерево Меркла для дельта-синхронизации
— фаза 7.

Читатель отбрасывает записи с неверной подписью или неканоничным телом и сообщает
о них; остальные записи принимаются.

## 8. Тестовые векторы

`spec/vectors/` содержит эталонные наблюдения, созданные из фиксированного seed
ключа. Любая реализация обязана получать те же `body_bytes`, `id` и `sig`
(Ed25519 детерминирован).

## 9. Местоположение

Положение — обычные утверждения (claims), поэтому подписаны, сливаются и могут
противоречить друг другу, как и всё остальное. Координаты никогда не «хранятся
в устройстве»: они вычисляются из наблюдений.

### 9.1 Утверждения

| ключ           | значение | смысл |
|----------------|----------|-------|
| `loc.geo`      | `lat,lon,radius_m` | WGS84, градусы с 6 знаками; радиус — круг ошибки (~95 %), метры |
| `loc.logical`  | текст ≤120 символов | место без координат: `HQ/2/R201` |
| `loc.region`   | текст ≤120 символов | страна или город |
| `location.text`| текст    | `sysLocation` из SNMP: читается как `loc.logical` |

Недопустимые значения (широта вне ±90, радиус ≤ 0 и т. п.) читатель игнорирует.
Методы: `manual` (человек), `gpsd` (одна GPS-отметка наблюдателя), `snmp` (sysLocation).

### 9.2 Уровни

| уровень   | условие |
|-----------|---------|
| `precise` | есть точка, радиус ≤ 30 м |
| `area`    | есть точка, радиус ≤ 3 км |
| `region`  | точка с радиусом > 3 км, либо только `loc.region` |
| `unknown` | ничего пригодного (`logical` может быть задан и так) |

Уровень выводится из радиуса, а не задаётся: лучшие данные автоматически повышают его.

### 9.3 Расчёт (нормативно для v1)

1. **Время.** «Сейчас» — самое позднее время в наборе (функция от набора, не от часов).
   Уверенность оценки умножается на `2^(−возраст/T½)`; ниже 0,05 оценка считается
   истёкшей. `T½`: `gpsd` — 2 ч; `manual` для самого наблюдателя — 7 сут; `manual`
   и `snmp` для остальных — 365 сут; прочее — 30 сут.
2. **Слияние оценок одного устройства.** Опорная — оценка с наименьшим радиусом среди
   имеющих уверенность ≥ ½ максимальной. С ней согласны оценки, чьи круги пересекаются
   с кругом опорной. Согласные усредняются с весами `c/r²`; радиус `1/√Σ(1/r²)`
   (не менее 1 м); уверенность `1−Π(1−c)`. Несогласные не участвуют, результат помечается
   `conflict`, уверенность ×0,6; источники остаются видимыми.
3. **Распространение по связям.** Позиция устройства с прямой оценкой переходит по
   явным связям графа (до 3 переходов), радиус растёт, уверенность падает:

   | связь       | +радиус | ×уверенность | переносит `logical` |
   |-------------|---------|--------------|---------------------|
   | `l2`        | 100 м   | 0,9          | да                  |
   | `wifi`      | 100 м   | 0,8          | нет (радио охватывает несколько комнат) |
   | `l2-behind` | 300 м   | 0,5          | нет                 |

   `l3` не переносит ничего — маршрутизатор может быть где угодно. Членство в одной
   сети тоже не переносит положение: сегмент может быть сколь угодно большим.
   Выведенная оценка помечается `derived`; прямые оценки всегда точнее и побеждают при слиянии.
4. Оценки с радиусом > 20 км при распространении отбрасываются.

### 9.4 Приватность

Координаты и названия мест — чувствительные данные: они путешествуют внутри карты.
Фильтры при экспорте (огрубление, удаление `loc.*`) — фаза 7.

## 10. Доверие и обмен

Набор наблюдений один для всех; разным читателям он может значить разное —
в зависимости от того, кому они верят. Доверие **локально** и никогда не входит в карту.

### 10.1 Уровни доверия к ключам

| уровень   | действие при построении графа |
|-----------|-------------------------------|
| `self`    | собственные ключи установки (текущий и предыдущие после ротации) |
| `trusted` | полный вес |
| `unknown` | по умолчанию: уверенность утверждений ×0,5; сильные идентификаторы склеиваются, только если это не противоречит уже сложившимся устройствам (`rkm`, `ssh`, `lldp`, `mac`, `lmac` с разными значениями) — иначе конфликт `untrusted-identity` |
| `blocked` | наблюдения игнорируются и никогда не передаются дальше |

Склейка идёт в два прохода — сначала доверенные, потом неизвестные, — чтобы результат
не зависел от порядка наблюдений. Без книги доверия (просмотр файла как есть) все ключи
считаются доверенными.

### 10.2 Отзыв и ротация

Наблюдение с методом `revoke`, `subject = ["rkm:<свой ключ>"]`:

| claim           | смысл |
|-----------------|-------|
| `key.revoked`   | Unix ms, с которого подписи ключа недействительны |
| `key.successor` | `rkm:<новый ключ>` — продолжение этого наблюдателя |

Учитывается, только если подписано тем самым ключом (ключ может отозвать лишь себя).
Наблюдения ключа с `time > key.revoked` игнорируются у всех, до кого дошёл отзыв.
Преемник наследует уровень отозванного ключа, если читатель не задал его явно; если
объявлено несколько разных преемников (ключом владеет ещё кто-то), не наследует никто.
При компрометации преемник не объявляется — доверие новому ключу выдаётся явно.

### 10.3 Что покидает машину

Подписанное чужое наблюдение нельзя изменить. Поэтому при экспорте и синхронизации:

- отбор по наблюдателям (`all` / `trusted` / `own`; `blocked` — никогда) и по времени;
- `location=drop|coarse:N`: собственные наблюдения переподписываются с удалёнными
  или огрублёнными координатами (центр клетки N×N, радиус r + N·√2/2 — исходный круг
  остаётся внутри; комнаты и этажи удаляются, регион остаётся); чужие наблюдения с
  координатами (и свои, подписанные отозванным ключом) не передаются вовсе.

Ed25519 детерминирован, поэтому одинаковое огрубление даёт одинаковые id —
повторный обмен ничего не передаёт.

### 10.4 Синхронизация

TLS 1.3, обе стороны предъявляют самоподписанный сертификат на ключе наблюдателя.
Сервер допускает ключи уровня `trusted`/`self` (книга перечитывается на каждом рукопожатии);
клиент закрепляет ключ сервера (полный ключ или имя/префикс из своей книги; также
принимается объявленный преемник закреплённого ключа). Проверка цепочки не нужна:
в TLS 1.3 собеседник доказывает владение закрытым ключом сертификата.

```
GET  /sync/v1/summary      256 дайджестов корзин (по первому байту id) разделяемого набора
GET  /sync/v1/bucket/{b}   id корзины
POST /sync/v1/fetch        {ids} → .rkm (только из разделяемого набора, сколько бы ни попросили)
POST /sync/v1/push         .rkm → добавить (если сервер разрешил)
```

Клиент сравнивает дайджесты, запрашивает id только различающихся корзин, забирает
недостающее и отправляет то, чего нет у сервера. Всё проверяется подписью при приёме.

## 11. Интернет-уровень

Карты из разных сетей соединяются через то, что глобально уникально: публичные
адреса (`gip:`). Ничего не сканируется: используются только собственные выходы сетей
и трассировки к явно указанным целям.

### 11.1 Выход сети в интернет (метод `wan`)

Шлюз спрашивают о его внешнем адресе — без открытия портов:

| источник  | как |
|-----------|-----|
| `nat-pmp` | RFC 6886, запрос внешнего адреса (op 0) к шлюзу по умолчанию, UDP 5351 |
| `upnp`    | UPnP IGD `GetExternalIPAddress`; описание и control URL — только на адресе шлюза |
| `stun`    | RFC 5389 Binding к серверу, **явно** указанному пользователем: адрес, видимый из интернета |

Наблюдения:
- `subject = [адрес выхода]` (`gip:` для публичного, `rip:<net>/…` для carrier-NAT/приватного),
  claims `role=wan-address`, `wan.source`, `wan.nat` (если не публичный), `link.wan` →
  шлюз (или адрес carrier-NAT, если STUN видит другой адрес);
- `subject = [net:<id>]`, claim `wan.<источник> = адрес`.

Связь `wan` не переносит местоположение. Сети за одним публичным адресом (дом,
кампус) сходятся на нём. Все сведения о выходе — отдельный метод, поэтому экспорт
может их исключить целиком (`--wan drop`).

### 11.2 Автономные системы

Принадлежность адреса к AS — справочные данные читателя (`rakkan asn import`, формат
ip2asn TSV), а не наблюдение: она меняется со временем и не является фактом, который
кто-то видел. В карты не входит. Резолвер (`Options.ASN`) помечает устройства с
публичными адресами и сети с известным выходом и группирует их по AS. Страна AS —
место регистрации, а не расположения: в местоположение (§9) она не превращается.

### 11.3 Масштаб (замеры v1)

| операция | 20 тыс. набл. | 100 тыс. | 400 тыс. |
|----------|---------------|----------|----------|
| построение графа | 0,07 с | 0,54 с | 2,9 с (1,1 ГБ) |
| загрузка из хранилища | — | 0,54 с | — |

Подписи проверяются при приёме (`import`, `sync`, `verify`), а не при каждой загрузке
своего хранилища: это дало ×10 на загрузке. `rakkan verify` без файлов проверяет всё
хранилище. Предел одной машины — порядка миллиона наблюдений; дальше нужен
инкрементальный резолвер (пересчёт только затронутых кластеров) — следующий шаг.

## 12. Тип устройства

Тип — вывод читателя, как и AS (§11.2): резолвер вычисляет его при каждом построении
графа из уже собранных утверждений и в карты его не записывает. Поэтому улучшенные
правила сразу применяются к старым картам.

Классы: `desktop`, `laptop`, `server`, `phone`, `tablet`, `tv` (телевизоры, приставки,
приёмники трансляций, игровые консоли), `iot` (колонки, камеры, датчики, розетки,
лампы), `printer`, `network` (шлюзы, коммутаторы, точки доступа). Если признаки
указывают только на группу, ответ честно обобщённый: `computer` (desktop, laptop или
server) или `mobile` (phone или tablet).

### 12.1 Утверждение `class`

| ключ    | значение | смысл |
|---------|----------|-------|
| `class` | имя класса | заявленный тип: вручную (`rakkan class DEVICE CLASS`, метод `manual`) или тип корпуса наблюдателя из SMBIOS (`self`, `C`=900) |

Если заявленный тип имеет вес больше 500 ‰ после поправки на доверие (§10.1), он
главнее вывода. Тогда несогласный вывод показывается как альтернатива. Заявление с
весом не больше 500 ‰ (например, от ключа со статусом `unknown`) — лишь один из
признаков.

### 12.2 Вывод (для v1 информативно, не нормативно)

Правила сопоставляют признаки с классами. Каждое срабатывание даёт голос с весом
`w·C/1000`, где `C` — уже учтённая доверием уверенность утверждения. Признаки:

- модель (`model`), включая идентификаторы Apple (`iPhone15,2`, `Mac14,2`,
  `AudioAccessory5,1`);
- слова в `name`, `hostname`, `mdns.name`, `mdns.instance`, `vendor`, `os.desc`,
  `upnp.*`, `dhcp.vendor`, `http.server`, `ssh.banner`, а также в `rdns` с половинным
  весом;
- объявленные mDNS-сервисы (`_ipp._tcp` → printer, `_androidtvremote2._tcp` → tv,
  `_esphomelib._tcp` → iot…);
- открытые порты (`62078` → mobile, `9100` → printer…);
- роли (`gateway` → network);
- MAC-префиксы виртуальных машин и контейнеров;
- случайный (локально администрируемый) MAC → mobile.

`ssid` не учитывается: это имя сети, а не устройства.

Комбинирование:
1. Один факт засчитывается один раз. Сначала по каждому значению утверждения
   оставляется сильнейший голос за класс, затем по каждому правилу — сильнейший
   голос по всем значениям.
2. Внутри класса голоса складываются как `1 − Π(1 − w)`. Класс-лист добавляется к
   своей группе (`computer`, `mobile`).
3. Группы ранжируются: `conf = s₁ · (1 − s₂/2)`, где `s₂` — оценка второй группы. При
   `conf < 0,25` тип неизвестен.
4. Группа уточняется до листа, если у лучшего листа `l₁ ≥ 0,4` и `l₁ − l₂ ≥ 0,2`.
   Тогда `conf = min(conf, l₁ · (1 − l₂/2))`.
5. Вторая группа с оценкой `≥ 0,3` показывается как альтернатива. В причинах (до 4)
   перечислены сработавшие признаки — тип всегда можно перепроверить.

Роль `router`, полученная из IPv6 Router Advertisement, — слабый признак (0,5): RA
рассылают и пограничные маршрутизаторы Thread (HomePod, Apple TV, хабы умного дома).
Сильный признак — роль `gateway`.
