# Rakkan Mesh — архитектура

Mesh-сеть для распределённых вычислений: узлы на Go, клиентский SDK для Node.js,
задачи — WebAssembly-модули, присылаемые в рантайме.

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Модель доступа | Закрытая сеть, открываемая подписью корня | Участники с сертификатами — доверенное ядро; гости входят по PoW, их работа проверяется |
| Связь Go ↔ Node.js | Демон + SDK по unix-socket (gRPC/Connect) | Нет cgo/N-API-сборки под платформы, падение демона не роняет приложение |
| P2P-слой | go-libp2p | QUIC/Noise, mDNS, Kademlia, NAT traversal, relay — готовы и проверены |
| WASM-рантайм | wazero | Чистый Go, без cgo, лимит памяти, прерывание по контексту |
| Целевой максимум | Распределённый инференс LLM | Определяет требования к планировщику и execution-классам (ниже) |

## Закрытая сеть и путь к открытой

- **Членство**: корневой ключ сети подписывает сертификаты узлов
  (`node_pubkey, roles, expiry`). Вход — по одноразовому invite-токену.
- **Отзыв**: список отозванных сертификатов распространяется через gossip, подписан корнем.
- **Транспорт**: libp2p Noise + опционально PSK (`pnet`) как второй периметр.
- **Открытие** (фаза 6, раздел «Открытая сеть» ниже): корень подписывает политику
  «сеть открыта, PoW N бит», и сеть начинает принимать гостей без сертификата.
  Участники с сертификатами остаются доверенным ядром, результаты гостей
  перепроверяются, их запросы ограничены кредитом, репутация — EigenTrust.

## Классы исполнения

Задачи сильно разные — от перебора хешей до LLM. Один механизм всё не покроет:

| Класс | Пример | Как исполняется |
|---|---|---|
| **Pure WASM** | подбор хеша, парсинг, сжатие, мелкие фильтры | Весь код в WASM, CPU-only, SIMD128 |
| **WASM + host kernels** | обработка фото, ресайз, свёртки | WASM оркеструет, тяжёлые примитивы — версионированные host-функции узла (`image.*`, `tensor.*`), объявленные как capabilities |
| **Native services** | инференс LLM, GPU-вычисления | Узел запускает доверенный нативный движок (llama.cpp/ggml-сайдкар); WASM-задача может вызывать его через capability `llm.*` |

Почему LLM не может быть «просто WASM»:
- нет доступа к GPU, а CPU-SIMD WASM в разы медленнее нативного AVX-512/AMX;
- wasm32 адресует максимум 4 ГиБ — меньше весов любой полезной модели;
- веса модели должны жить на узле постоянно, а не пересылаться с каждой задачей.

Узлы публикуют **capability-манифест**: CPU/GPU, VRAM, RAM, доступные host-kernels
(с версиями), закешированные модели/слои. Планировщик выбирает узлы по нему.

## Распределённый LLM (план-максимум)

- **Pipeline parallelism по слоям** (подход Petals/exo): каждый узел держит
  диапазон слоёв, активации передаются по цепочке. Активация на токен — это
  `hidden_size × 2 байта` (≈8–16 КБ), что приемлемо даже для WAN. Tensor parallelism
  требует широкого канала, поэтому годится только внутри одной LAN или машины.
- **Задержка** на токен ≈ сумма хопов → планировщику нужна карта задержек
  (координаты Vivaldi) и выбор цепочки с минимальным суммарным RTT.
- **Отказоустойчивость**: каждый диапазон слоёв держат ≥2 узла. При падении
  узла цепочка перестраивается, KV-кеш на замене восстанавливается повторным
  prefill уже сгенерированного контекста.
- **Веса**: content-addressed, порезаны по слоям, раздаются внутри сети по
  принципу BitTorrent. Узел скачивает только свои слои.
- **Верификация**: GPU-вычисления недетерминированы (неассоциативность float),
  побайтовое сравнение реплик не работает. В закрытой сети — доверие по
  сертификату; для открытой — сравнение с допуском (logits/top-k) и выборочная
  перепроверка.

## Модель задач

- **Task** — один вызов WASM-модуля: `(module_hash, entry, input, limits, capabilities)`.
- **Job** — граф задач: map/reduce, DAG. Перебор хеша = map по диапазонам
  с ранней отменой остальных, когда ответ найден.
- **Данные** отделены от управления: модули и большие входы (фото, веса) лежат
  в content-addressed хранилище и передаются потоками; в сообщении о задаче —
  только хеши.

## WASM-песочница (`internal/sandbox`)

Реализовано:
- единственное разрешённое пространство импортов `rakkan` (`input_len`,
  `input_read`, `output_write`, `log`); WASI, импорт памяти и чужие модули
  отклоняются до инстанцирования — у гостя нет часов, ФС, сети, случайности;
- лимит линейной памяти на задачу (`memory.grow` сверх лимита возвращает -1);
- **детерминированный gas** (`internal/meter`, расписание стоимостей v1): модуль
  переписывается при загрузке — каждый линейный сегмент кода платит свою точную
  стоимость при входе, проверки стоят на входе в функцию, в заголовках циклов и
  на bulk-операциях (`memory.fill/copy/grow`, table-*), которые тарифицируются по
  длине; вызовы хоста тоже платят. Накладные расходы ≈1,7× на плотном цикле;
- таймаут и отмена доставляются через флаг прерывания, который проверяется вместе
  с gas (гость его только читает, поэтому запись сторожа не теряется), без
  `WithCloseOnContextDone`, который замедляет циклы wazero ~30×;
- полный разбор всех секций до передачи в wazero: декодер wazero 1.12
  предвыделяет память по объявленным счётчикам, и модуль из 26 байт мог положить
  процесс узла (OOM);
- лимиты на размер модуля, входа, выхода, лога;
- политика узла (`Limits.Within`): клиент не может запросить больше, чем разрешил оператор.

- **структурные лимиты** (`meter.Max*`): вложенность ≤ 1024, `br_table` ≤ 16 384
  целей, ≤ 4 таблиц по ≤ 2¹⁸ элементов (объявленный `max` урезается), одна
  память без shared/64-bit, ≤ 128 параметров/результатов, ограничения на число
  типов, импортов, функций, глобалов, экспортов, сегментов, локальных, размер тела.
  Компилятор wazero сверхлинеен по вложенности, `br_table` и «локальные × ветвления»;
  модуль на 30 КБ мог компилироваться секунды, а на 300 КБ — минуты. Лимиты срезают
  худшие соотношения, а компиляция засчитывается в таймаут задачи: узел убьёт
  воркер, если она не уложится. Компиляция может требовать и сотни мегабайт —
  это останавливает лимит памяти воркера (`ErrWorkerOOM`);
- **кеш**: `Runner` хранит инструментированные модули (LRU, 64 МБ) и
  скомпилированный код wazero, поэтому повторный запуск модуля в том же процессе
  пропускает и инструментацию, и компиляцию.

- **канонизация NaN**: после каждой операции, способной породить NaN
  (арифметика, округления, demote/promote, их SIMD-версии), результат заменяется
  каноническим NaN, если он NaN. Без этого 0/0 даёт 0xffc00000 на x86 и
  0x7fc00000 на ARM — узлы разной архитектуры расходились бы побайтово. Вместе с
  gas это ≈1,37× на плотном float-цикле.

Найденные проблемы wazero описаны для отправки в `docs/upstream/wazero-issues.md`.
5. **Capabilities**: host-kernels (`image.*`, `tensor.*`, `llm.*`) выдаются
   задаче явно и тарифицируются в gas.

## Изоляция процессов (`internal/isolate`)

Узел исполняет задачи не у себя, а в воркерах — это повторный запуск того же
бинарника (`isolate.IsWorker` / `RunWorker`). Пул держит свежие процессы «тёплыми».

`Pool.Run(ctx, owner, task)`: задача без владельца идёт в процесс, который ещё
ничего не исполнял. Задачи с владельцем могут переиспользовать процесс, уже
исполнявший **тот же модуль для того же владельца** (до `TasksPerWorker` задач,
простаивающие отпускаются через `IdleTimeout`) — повторный запуск тогда идёт без
старта процесса, инструментации и компиляции (на тестовом модуле 588 мс → 1,2 мс).
Процессы никогда не делятся между владельцами или модулями: задача, захватившая
воркер, достанет лишь данные, которые её владелец и так отдавал тому же коду.

Общий файловый кеш скомпилированного кода между процессами сознательно не
сделан: это исполнение машинного кода, записанного процессом, который
компилировал недоверенный модуль. Безопасная схема (компиляция в отдельном
свежем процессе, хранение по хешу модуля, вычисленному узлом, видимость только
задачам того же модуля) упирается в непубличный формат ключей кеша wazero.

Слои (`Isolation`):
- **namespaces**: user, mount, PID, network, IPC, UTS. Корень — пустой tmpfs
  только для чтения, в нём лишь бинарник воркера (и загрузчик с libc, если
  бинарник динамический). Сети нет совсем.
- **никаких capabilities**: воркер стартует root-ом своего user namespace,
  готовит корень, ставит securebits `NOROOT` и делает re-exec — после этого
  capabilities пусты во всех потоках. (Сбросить их иначе нельзя: capset
  действует на поток, а `AllThreadsSyscall` недоступен, когда слинкован cgo.)
- **seccomp-bpf**: allow-list того, что нужно рантайму Go и JIT (память, потоки,
  сигналы, часы, I/O на уже открытых дескрипторах). `open` → EPERM, `clone`
  разрешён только для потоков, всё остальное (сокеты, fork, mount, ptrace, bpf…)
  убивает процесс.
- **rlimits**: core, fsize, nofile, memlock; без cgroup — лимит адресного
  пространства.
- **cgroup v2** (опционально): `memory.max` без swap, `oom.group`, `pids.max`,
  `cpu.max`; воркер попадает в свою cgroup атомарно при clone
  (`CLONE_INTO_CGROUP`). OOM распознаётся и возвращается как `ErrWorkerOOM`.

Узел не доверяет ответам воркера: размеры и gas сверяются с лимитами задачи,
жёсткий дедлайн (таймаут + 2 с) убивает зависший воркер, падения
классифицируются (в том числе «убит seccomp»).

Особенность Go: скомпилированный WASM нельзя вытеснить, поэтому stop-the-world
фаза GC, начавшаяся во время работы гостя, ждёт его окончания вместе со всеми
горутинами. В воркере GC на время задачи выключен (память держат cgroup/rlimit).
Внутрипроцессный `sandbox.Runner` поэтому годится только для локальных запусков,
но не для узла.

Запуск с cgroups: узлу нужна делегированная ему одному cgroup, например
`systemd-run --user --scope -p Delegate=yes rakkan-node …` или `Delegate=yes`
в unit-файле, и параметр `-cgroup self`. Тест: `RAKKAN_TEST_CGROUP=1` внутри
такой cgroup (см. `TestCgroupLimits`).

## Сеть (`internal/membership`, `internal/mesh`)

**Членство.** ID сети — peer ID корневого ключа (Ed25519 встроен в ID, так что
строка ID и есть якорь доверия). Корень подписывает сертификаты узлов:
`{сеть, peer ID, роли, серийный номер, срок}`. Узел с ролью `admin` может
выпускать сертификаты участников без корневого ключа, но не админов — цепочка не
длиннее двух звеньев, и делегированный сертификат не переживает сертификат
админа. Отзыв — подписанный корнем кумулятивный CRL с возрастающим номером;
отзыв админа аннулирует всё, что он выпустил. Подписи разделены по доменам
(сертификат нельзя выдать за CRL и наоборот). Сертификат доказывает членство
только вместе с соединением: libp2p аутентифицирует peer ID, и он обязан
совпасть с субъектом.

**Допуск.** Сразу после соединения стороны обмениваются сертификатами (и своим
последним CRL) по `/rakkan/auth/1.0.0`. Кто не прошёл за `AuthTimeout` — отключён
и временно заблокирован гейтером соединений; отозванный — навсегда. Все
прикладные протоколы (DHT, pubsub и протоколы, зарегистрированные через
`Node.Handle`) видят хост-обёртку, пропускающую потоки в обе стороны только для
аутентифицированных участников: посторонний не может даже спросить у DHT адреса
участников.

**Обнаружение.** Bootstrap-узлы, mDNS в локальной сети, приватная Kademlia DHT
(свой префикс протокола, в таблице маршрутизации только участники) с
rendezvous-записью сети. Раунды поиска начинаются каждые 2 с и замедляются до
`DiscoveryInterval`; допуск нового участника запускает раунд сразу.
(`util.Advertise` из libp2p не годится: после первой неудачи на пустой таблице
он ждёт 2 минуты.)

**Восстановление.** Ping участников с измерением RTT; три пропуска подряд —
соединение закрывается. Известные участники переподключаются с экспоненциальной
задержкой и джиттером (до `MaxBackoff`), свежие адреса ищутся в DHT. Узел,
вернувшийся на тот же адрес, будет найден без его участия. Сертификаты живых
участников перепроверяются: истёкший или отозванный отключается.

**NAT.** UPnP, hole punching (DCUtR), relay v2 через участников с `-relay`
(ACL пускает только участников). Стандартная автоматика libp2p рассчитана на
большую публичную сеть и в маленькой закрытой не работает — это показала
NAT-лаборатория, поэтому:
- *достижимость* определяется по адресам прослушивания (публичный адрес —
  публичный узел, только приватные — за NAT), а не AutoNAT: тому нужны несколько
  проверяющих, а единственный проверяющий звонит обратно по тому же 5-tuple, NAT
  пропускает, и узел за NAT считает себя публичным. Переопределяется флагом
  `-reachability`;
- *relay-сервис* при `-relay` запускается сразу, а не после подтверждения AutoNAT;
- *AutoRelay* довольствуется одним кандидатом, без 3-минутной задержки, и
  кандидаты — только участники, реально поддерживающие relay;
- *внешний адрес* узла за NAT сообщают в обмене сертификатами аутентифицированные
  участники (хватает одного). Своему механизму libp2p нужны 4 наблюдателя, и
  учитывает он любого подключившегося;
- loopback-адреса не публикуются (иначе другие звонили сами себе);
- *кеш участников* (`-peers peers.json`) переживает перезапуск: узлы
  возвращаются в сеть, даже когда все bootstrap-узлы лежат.

**NAT-лаборатория** (`test/natlab`) — эмуляция интернета, роутеров с NAT и
машин за ними в network namespaces одного непривилегированного user namespace
(root не нужен). NAT `cone` — обычный masquerade с сохранением порта, как у
домашних роутеров; `symmetric` — новый порт на каждое направление, как у CGNAT.
`test/natlab/run-all.sh <бинарник>` проверяет:

| Сценарий | Результат |
|---|---|
| cone ↔ cone | прямое соединение (hole punching) |
| cone ↔ symmetric | через relay |
| symmetric ↔ symmetric | через relay |
| якорь падает после установления связи | прямое соединение сохраняется |
| оба узла перезапущены, якорь лежит, с кешем | прямое соединение восстановлено |
| то же без кеша | изоляция (контрольный прогон) |

**Отзыв в работе.** Оператор выполняет `network revoke`, переписывая `crl.json`;
демон, запущенный с `-crl crl.json`, замечает новую версию, публикует её через
GossipSub (валидатор проверяет подпись корня), и вся сеть отключает отозванного.
CRL также передаётся в каждом обмене сертификатами, так что новые и вернувшиеся
узлы узнают о нём при подключении.

Пример:

```sh
rakkan-node network init -out root.key            # печатает ID сети
rakkan-node id -key n1.key                         # на каждом узле: его peer ID
rakkan-node network issue -peer <id1> -roles member,admin -out n1.cert
rakkan-node network issue -key n1.key -issuer-cert n1.cert -network <net> -peer <id2> -out n2.cert
rakkan-node daemon -network <net> -key n1.key -cert n1.cert -crl crl.json
rakkan-node daemon -network <net> -key n2.key -cert n2.cert -bootstrap /ip4/…/tcp/…/p2p/<id1>
rakkan-node network revoke -crl crl.json <serial>  # серийный номер: network show <cert>
```

## Распределённое исполнение (`internal/exec`, `internal/api`, `sdk/js`)

**Протокол `/rakkan/exec/1.0.0`**, одна задача на поток: заголовок (хеш модуля,
размеры, лимиты) → предложение исполнителя (`send_module` / `ready` / `busy` /
`rejected`) → модуль (только если его у исполнителя нет) и вход → результат.
Модули адресуются по SHA-256: исполнитель проверяет хеш присланного модуля и
кеширует его, так что повторные задачи передают только вход. Владелец задачи для
пула воркеров — peer ID отправителя: его задачи с тем же модулем переиспользуют
тёплый воркер. Отправитель держит поток открытым до результата; сброс потока
отменяет задачу у исполнителя.

**Загрузка** узлов (слоты, занятость, очередь, лимиты, CPU, архитектура)
распространяется через GossipSub раз в несколько секунд и сразу после изменений.

**Планировщик** работает у отправителя: среди участников (и себя), чьи лимиты
допускают задачу, выбирается узел с наибольшим числом свободных слотов, при
равенстве — уже имеющий модуль, затем с меньшим RTT; себе — небольшой бонус (нет
передачи). Свои задачи «в полёте» к каждому узлу учитываются сразу, не дожидаясь
госсипа. Если все заняты — ожидание; если лимиты задачи превышают политику всех
узлов — ошибка с объяснением.

**Отказоустойчивость.** Сбой исполнителя (обрыв, падение воркера, нарушение
протокола, остановка узла) — повтор на другом узле, до `MaxAttempts`. «Занят» не
считается попыткой. Детерминированные ошибки задачи (gas, trap, таймаут,
некорректный модуль) не повторяются — любой узел выдал бы то же. Исполнитель,
прервавший задачу по своей причине, не отправляет «отменено» как результат, а
сбрасывает поток.

**Репликация.** `Replicas: k` — задача на k разных узлах; сравниваются код
выхода, gas и SHA-256 вывода (или вид ошибки). Принимается исход большинства от
k, несогласные реплики помечаются. Это работает благодаря детерминизму фазы 1:
gas и NaN побайтово совпадают на разных машинах и архитектурах.

**Map** — один модуль на много входов с ограничением параллелизма (по умолчанию
— свободные слоты сети), результаты потоком; `StopWhen` останавливает и
отменяет остальное.

**Локальный API** — HTTP на unix-сокете с правами 0600: `/v1/modules`,
`/v1/run`, `/v1/map` (NDJSON-поток), `/v1/status`. Разрыв соединения отменяет
задачи. **JS SDK** (`sdk/js`) — ESM без зависимостей с типами TypeScript.

Пример (`sdk/js/examples/search.js`, 3 узла по 4 воркера на одной машине):
поиск прообраза хеша среди 2³⁰ значений, 1024 диапазона — найден за 0,47 с,
после 873 диапазонов остальные отменены.

## Данные (`internal/blob`)

**Блобы с адресацией по содержимому.** Данные режутся на чанки по 1 МиБ, каждый
назван своим SHA-256; манифест — размер и список хешей чанков, ID блоба —
SHA-256 манифеста. Отсюда: каждый чанк проверяется при получении (данные от
недоверенного узла проверены до записи на диск), одинаковые чанки хранятся
один раз, прерванная загрузка продолжается с полученных чанков, чанки можно
брать у нескольких узлов одновременно.

**Хранилище** на диске (`-data`, бюджет `-store-gb`): вытесняются давно не
использованные блобы, кроме закреплённых (используемых задачами и загрузками).
Чанки незавершённой загрузки сохраняются для докачки — и после перезапуска
узла, — но вытесняются первыми и удаляются через час. Пока блоб собирается, его
чанки удерживаются, чтобы вытеснение другого блоба с общими чанками их не
удалило.

**Передача** `/rakkan/blob/1.0.0`: манифест, затем пачки по 8 чанков; до двух
потоков на источник, не больше 8 всего. Пачка, которая не пришла, пришла не
целиком или с испорченным чанком, уходит другому источнику; источник после трёх
неудач исключается. Одновременные загрузки одного блоба объединяются. Любой
участник может получить блоб, если знает его ID — ID это хеш содержимого.
На одной машине (loopback, QUIC): ≈415 МБ/с с одного источника, ≈512 МБ/с с двух
— упор в CPU (шифрование и SHA-256), а не в сеть.

**В задачах.** Вход больше 1 МиБ отправитель сохраняет как блоб, исполнитель
забирает его у отправителя (и у перечисленных источников); выход больше 1 МиБ
исполнитель сохраняет как блоб, отправитель сразу забирает его, так что
результат не зависит от того, останется ли исполнитель в сети. Реплики
сравнивают ID выхода — он одинаков для одного содержимого, пришло ли оно
блобом или в сообщении. Воркер по-прежнему получает вход целиком (в пределах
`MaxInputBytes`; у изолированного воркера нет файловой системы), поэтому бюджет
памяти воркера учитывает потолки входа и выхода (`-max-input-mb`,
`-max-output-mb`).

**API/SDK.** `POST /v1/blobs` пишет тело запроса в хранилище по чанкам, не
держа его в памяти; `GET /v1/blobs/{id}` поддерживает Range. SDK: `putBlob`
(байты, поток, `{path}`), `getBlob` (поток, диапазоны), `readBlob`; `run`
сам загружает вход больше 256 КБ блобом и скачивает выход-блоб, если не
указан `outputAsBlob`.

## Чтение блобов изнутри задачи и host-kernels

**Прикреплённые блобы.** Задача получает до 16 блобов и читает их кусками:
`blob_count`, `blob_size`, `blob_read(index, dst, offset, len)` — прямо в
линейную память, без промежуточной копии. Цепочка ленивая насквозь: воркер
запрашивает у узла диапазон по своему каналу (протокол воркера стал
двунаправленным: кадры «чтение блоба» и «результат»; узел проверяет номер,
смещение и размер ≤ 1 МиБ и убивает нарушителя), а узел читает блоб через
`blob.OpenRemote`, который докачивает из сети только нужные чанки (с упреждением
на 4 чанка) у отправителя и указанных источников. Задача, прочитавшая 1 МБ из
блоба на 10 ГБ, скачает около 1 МБ. Блоб, прочитанный целиком, регистрируется в
хранилище исполнителя, так что общий блоб для map скачивается один раз на узел.
Недоступность блоба — ошибка узла (`blob_unavailable`): задача повторяется на
другом. Чтение тарифицируется как `input_read`.

**Image kernels** (`rakkan_image_v1`, capability `image/1`): декодирование PNG/
JPEG, масштабирование, обрезка, оттенки серого, размытие, доступ к пикселям,
кодирование прямо в выход. Нативный код в разы быстрее того же в WASM, но
выполняется в изолированном воркере, а не в узле: декодеры изображений —
классическая поверхность атаки. Защиты: размеры читаются из заголовка до
декодирования (PNG, объявляющий 30000×30000, отклоняется, не потратив память),
пиксели всех изображений задачи ограничены её лимитом памяти, стороны ≤ 32768,
gas — за пиксель каждой операции. Детерминизм: масштабирование (точный box-
фильтр по площади перекрытия) и размытие (скользящие суммы) — целочисленные,
потому что Go вправе сливать умножение и сложение с плавающей точкой в FMA на
arm64, и реплики на разных архитектурах разошлись бы; кодеки стандартной
библиотеки целочисленные. Узлы должны запускать одну версию Go (как и одну
версию wazero).

**Capabilities.** Узел объявляет в госсипе загрузки свои optional host API
(их можно ограничить через `exec.Config.Capabilities`). Отправитель выводит нужные
задаче capabilities из пространств импорта модуля — тем же проверенным fuzzing'ом
парсером инструментатора, без компиляции недоверенного кода в узле — и не
отправит задачу узлу без них; если таких нет, ошибка называет недостающую
capability. Исполнитель и сам отклоняет такие задачи (как ошибку маршрута,
не задачи — отправитель пробует другой узел).

Пример (`sdk/js/examples/thumbnails.js`, 3 узла по 2 воркера): 12 фото по
12 Мп — миниатюры 320×240 за 1,37 с.

**Tensor kernels** (`rakkan_tensor_v1`, capability `tensor/1`): матрицы f32/i8/
i32 в таблице хоста (общий бюджет с изображениями), `matmul`/`matmul_t`, `add`
с broadcast строки, `scale`, `relu`, `softmax`, `quantize`, `argmax`; веса
загружаются из прикреплённого блоба прямо на хосте (`from_blob`). Детерминизм
плавающей точки — главное: каждое произведение f32 явно приводится перед
сложением (спецификация Go разрешает компилятору сливать `x*y+z` в FMA даже
через границы операторов, и на arm64 он это делает; приведение запрещает),
порядок суммирования фиксирован, `exp` для softmax своя (полином после
редукции диапазона; `math.Exp` на amd64 — ассемблер), NaN канонизируются,
int8-произведения накапливаются в int32 точно. Проверено: результаты kernels
побитово совпадают с эталоном на Go (и при `GOAMD64=v3`, где компилятор умеет
FMA), с тем же умножением на чистом WebAssembly (в WASM нет FMA), и с эталоном на
JavaScript через `Math.fround` — на узлах сети.

**Калибровка gas.** Цены kernels подобраны так, чтобы единица gas стоила
примерно столько же времени, сколько в WebAssembly (≈0,15 нс на эталонной
машине): иначе задача на kernels при том же бюджете занимала бы узел в разы
дольше. Умножение 256³: WASM 150 мс / 1,06·10⁹ gas, kernel 19 мс / 1,3·10⁸ gas.
Декодирование JPEG (12 Мп — ~260 мс) упирается в кодек стандартной библиотеки
Go (без SIMD); libjpeg-turbo потребовал бы cgo в изолированном воркере.

**AssemblyScript** (`sdk/as`): привязки ко всему ABI (вход/выход/лог, блобы,
`Image`, `Tensor`) и замена `abort` (компилятор импортирует его из `env`,
которого в песочнице нет). Модули настоящего компилятора используют start-
функцию, bulk memory и аллокатор — Go-тесты гоняют собранные примеры через
песочницу и сверяют с эталонами. Ошибки задач несут хвост её лога, так что
сообщение `abort` с местом в исходнике доходит до пользователя. Rust/TinyGo в
окружении разработки не было; ABI для них тот же.

Примеры (3 узла на одной машине): миниатюры 12 фото по 12 Мп — 1,37 с;
подсчёт слова в 9,6 МБ как map по диапазонам общего блоба; инференс MLP
784→256→10 — ~19 600 образцов/с, логиты побитово равны эталону на JS.

Что дальше: native-сервисы и распределённый LLM (фаза 5) — kernels здесь
скалярные и годятся для небольших моделей; для LLM нужны SIMD/GPU и движок
вроде llama.cpp как доверенный сервис узла. Также: поиск источников блоба
через DHT, квоты и приоритеты между владельцами, учёт ресурсов (кредиты),
очередь задач, переживающая перезапуск отправителя.

## Распределённый LLM (`internal/llm`, `internal/num`)

**Движок** на Go для decoder-only трансформеров семейства LLaMA: RMSNorm,
RoPE, attention с KV-кешем и GQA, SwiGLU. Поддержаны также вариации Qwen2
(bias в проекциях q/k/v) и Qwen3 (RMSNorm каждой головы q и k, `head_dim`, не
равный `dim/heads`); θ RoPE и eps берутся из конфига.

Источники весов:
- чекпойнты llama2.c (f32): TinyStories, экспорты LLaMA-2;
- модели Hugging Face (`config.json`, `tokenizer.json`, safetensors, в том
  числе разбитые на шарды) с типами `llama`, `mistral`, `qwen2`, `qwen3`.

Матрицы хранятся в f32 или bf16 и умножаются в f32. Перевод bf16 в f32 точный,
поэтому bf16 вдвое экономит память и полосу, не трогая детерминизм. При импорте
их можно квантовать (раздел «Квантование» ниже). Импорт
читает safetensors по одному тензору, весь файл в памяти не нужен. Строки q/k
(а также их bias и веса нормализации голов) переставляются из раскладки RoPE
Hugging Face (`rotate_half`) в раскладку движка (соседние пары). Токенизатор —
byte-level BPE по `tokenizer.json` (NFC, шаблоны разбиения Qwen и Llama 3,
спецтокены). Шаблон разбиения содержит lookahead, которого нет в `regexp` Go,
поэтому он реализован вручную. Стоп-токены берутся из `generation_config.json`,
формат чата (ChatML, Qwen3 без размышлений, Llama 3) из `tokenizer_config.json`.
Длина KV-кеша равна длине генерации (промпт плюс `max_tokens`), а не всему
контексту модели (32–40 тыс. позиций у Qwen).

Проверка:
- **Qwen2.5-0.5B-Instruct и Qwen3-0.6B.** Логиты на всех позициях промпта
  сверены с независимой реализацией на numpy (`tools/llmref/hf_reference.py`:
  определение из transformers, `rotate_half` без перестановки, вся
  последовательность с причинной маской, BLAS). Максимальное расхождение
  1,4·10⁻⁴ и 3,3·10⁻⁵ при логитах до 30–36, первый токен совпадает везде.
  Обе модели отвечают «Paris» на вопрос о столице Франции и пишут связные
  предложения. Qwen2.5, разрезанный на три узла, даёт ровно те же токены, что
  целиком в одном процессе. Тест `TestHFModels` берёт модели из каталога
  `RAKKAN_HF_MODELS`.
- **stories15M.** Жадная генерация даёт связный текст («Once upon a time,
  there was a little girl named Lily...»), токенизатор выдаёт ID LLaMA.
  Скомпилировать эталонный `run.c` из llama2.c не дал классификатор
  безопасности окружения (внешний код).
- **Синтетическая модель с GQA** совпадает с наивной реализацией на float64.

**Детерминизм** (`internal/num`): произведения явно приводятся (нет FMA), порядок
сумм фиксирован, свои `exp`, `sin`, `cos` (редукция Коди–Уэйта, полиномы Cephes
с округлением каждого шага) вместо пакета `math`, `math.Sqrt` точен везде.
Скалярные произведения весов суммируются в 32 независимые суммы (элемент i
идёт в сумму i mod 32) с фиксированным деревом сложения в конце. Это ровно
четыре 8-полосных аккумулятора AVX2 с отдельными умножением и сложением, так
что ассемблер для amd64 (`dot_amd64.s`) и переносимый Go дают одинаковые биты;
тест сверяет их. Скорость в 19 раз выше прежнего последовательного `Dot`.
Матрично-векторное произведение параллельно по строкам без влияния разбиения
на биты. Поэтому модель, разрезанная по любым узлам любых архитектур, даёт
ровно те же логиты, что целиком в одном процессе.

**Модель как блобы**: эмбеддинги, каждый слой, голова, токенизатор — отдельные
блобы, ID модели — хеш манифеста. Узел-стадия скачивает только свои слои.

**Стадии** (`/rakkan/llm/1.0.0`, демон с `-llm`): один поток — одна стадия одной
генерации; KV-кеш живёт, пока открыт поток, и недоступен другим участникам.
Веса и кеши в бюджете памяти (`-llm-mem-gb`), неиспользуемые слои вытесняются.
Узлы объявляют загруженные диапазоны слоёв через gossip, координатор предпочитает
узлы, где нужные слои уже загружены.

**Координатор** держит эмбеддинги и голову, делает prefill промпта одним
запросом на стадию, затем генерирует по токену через стадии. Он хранит входы
каждой стадии, поэтому **отказ узла посреди генерации** стоит одной стадии: её
слои поднимаются на другом узле, ей переигрываются её прошлые входы, соседние
стадии ничего не пересчитывают — и текст продолжается ровно таким, каким был бы.
Дедлайн шага адаптивный (10× обычного времени на токен + 2 с): убитый процесс не
закрывает соединение, и без этого QUIC заметил бы смерть только через ~30 с.

**Квантование** (`quant` при импорте; `internal/num/quant.go`). Форматы:
- `q8_0`: блоки по 32 веса со своим масштабом float32, значения int8;
- `q4_0`: 4 бита, два значения на байт. Масштаб блока подбирается методом
  наименьших квадратов: несколько стартов, чередование округления и
  оптимального масштаба;
- `q4_m`: как `q4_0`, но проекции V и down остаются в `q8_0`, как Q4_K_M в
  llama.cpp держит их точнее.

При 4 битах эмбеддинги и классификатор хранятся в `q8_0`.

Как считается. Вход матрично-векторного произведения тоже квантуется в
`q8_0`, поэтому сумма внутри блока — точное целое, одинаковое на любом
процессоре. В плавающей точке только объединение: вклад блока
float32(сумма)·float32(dw·dx) идёт в сумму номер `b mod 8`, суммы
складываются фиксированным деревом. AVX2 (`VPMADDUBSW`/`VPMADDWD`, четыре
блока за итерацию) и переносимый Go дают одинаковые биты, это сверяет тест.
Квантование при импорте тоже детерминировано (произведения округляются явно,
блоки независимы и делятся между потоками), так что одна модель, импортированная
на разных узлах, получает один ID.

Качество и размер. KL-дивергенция распределения следующего токена от эталона
на numpy, средняя по позициям промпта:

| | Qwen2.5-0.5B | KL | Qwen3-0.6B | KL |
|---|---|---|---|---|
| bf16 | 942 МиБ, 34 ток/с | 0 | 1136 МиБ, 28 ток/с | 0 |
| q8_0 | 530 МиБ, 40 ток/с | 0,013 | 639 МиБ, 35 ток/с | 0,010 |
| q4_m | 410 МиБ, 44 ток/с | 0,44 | 485 МиБ, 37 ток/с | 0,22 |
| q4_0 | 359 МиБ, 45 ток/с | 0,87 | 429 МиБ, 39 ток/с | 0,48 |

Все варианты отвечают «Paris» и пишут связный текст. Q8 практически без потерь.
4 бита на моделях в полмиллиарда параметров заметно сдвигают распределение;
большие модели переносят их лучше. На моделях такого размера выигрыш в скорости
умеренный: веса частично помещаются в кеш. Основная выгода — память и полоса,
которые на больших моделях и определяют скорость. Qwen2.5 в `q4_m`, разрезанный
на три узла, даёт те же токены, что целиком в одном процессе.

Измерения (один компьютер, 16 потоков, AVX2, без GPU):
- Qwen2.5-0.5B: локально ≈34 токена/с, на трёх стадиях ≈13 токенов/с (все узлы
  в одном процессе делят ядра, на каждый токен три сетевых перехода);
- Qwen3-0.6B: локально ≈29 токенов/с;
- SIGKILL узла-стадии посреди генерации (stories15M): замена за ~2 с, текст
  идентичен непрерванному.

Ограничения и что дальше:
- **размер модели** ограничен только суммарной памятью узлов: каждый держит
  лишь свои слои, координатор — эмбеддинги и голову. Например, 70B в bf16
  (140 ГБ) встаёт на десяток узлов по 16 ГБ, а в `q4_m` (≈40 ГБ) — на три.
  На CPU такая модель всё равно медленная: каждый токен читает все веса.
  Точнее Q4 были бы схемы с суперблоками (K-quants из llama.cpp);
- **на GPU выносятся только произведения матриц** (раздел «GPU» ниже). Внимание,
  нормализации и RoPE считает CPU, и каждый слой — четыре обмена с GPU. Целиком
  слой на GPU убрал бы эти обмены;
- **архитектуры:** нет MoE (Mixtral, Qwen3-30B-A3B), Gemma, Phi, rope scaling
  (Llama 3.1+, YaRN; такие модели при импорте отклоняются с объяснением);
- **токенизаторы:** нет SentencePiece-BPE с byte fallback (Llama 2, Mistral и
  TinyLlama в формате HF) и GPT-2-шаблона разбиения (SmolLM);
- стадии вызываются координатором по очереди (звезда); цепочка стадий
  напрямую уменьшила бы задержку на токен в WAN;
- выход стадии на участнике с сертификатом не проверяется (доверие корню); стадии
  гостей проверяет свидетель (раздел «Открытая сеть»);
- движок работает в процессе узла, а не в изолированном воркере: это доверенный
  код (Go, без cgo), входы (размеры, позиции) проверяются;
- импорт llama2.c читает чекпойнт целиком в память. Импорт safetensors идёт
  потоково, но файлы сначала загружаются на узел, который импортирует модель.

## GPU и узлы разной мощности (`internal/gpu`, `internal/llm/plan.go`)

**Бэкенд — Vulkan compute.** Его поддерживают NVIDIA, AMD, Intel, Apple
(через MoltenVK), мобильные GPU и даже программные реализации вроде lavapipe из
Mesa, на которой GPU-код проверяется без видеокарты. Vulkan вызывается через
purego, без cgo, поэтому узел по-прежнему собирается статически. Машина без
Vulkan просто считает на CPU. Шейдеры на SPIR-V генерирует сам Go-код
(`spirv.go`, небольшой построитель): компилятор шейдеров при сборке не нужен,
и ядра строятся под возможности конкретного устройства.

**GPU даёт те же биты, что CPU.** Ядра (`kernels.go`) повторяют порядок
вычислений `internal/num`:
- для f32 и bf16 поток-полоса j суммирует элементы j, j+32, … по порядку, затем
  то же дерево сложения;
- для Q8/Q4 точные целые суммы блоков объединяются по восьми полосам в том же
  порядке.

Каждое умножение и сложение помечено `NoContraction`, поэтому драйвер не вправе
слить их в FMA. Если устройство умеет, включаются режимы `SPV_KHR_float_controls`:
сохранение денормалов, округление к ближайшему чётному, сохранение знака нуля,
бесконечностей и NaN. Устройство без этих гарантий не выбирается по умолчанию
(`Info.Exact`).

Тесты сверяют GPU с CPU побитно на видеокарте AMD (RADV) и на lavapipe:
- отдельные произведения во всех четырёх форматах, со специально подобранными
  денормалами и отрицательными нулями;
- матрицы больше лимита одного буфера (у lavapipe это 128 МБ, такие матрицы
  делятся на части) и больше 65535 рабочих групп;
- стадии модели во всех форматах;
- настоящий Qwen2.5-0.5B в bf16 и `q4_m`: логиты на всех позициях совпадают
  с CPU до бита.

Поэтому GPU- и CPU-узлы взаимозаменяемы в одном конвейере. Восстановление после
отказа, свидетели и совпадение распределённого запуска с локальным работают
при любом их смешении.

**Что на GPU.** Произведения матриц, то есть почти вся арифметика модели. Веса
стадий живут в памяти GPU, а копия в RAM освобождается: узел с маленькой RAM и
большой видеокартой держит много слоёв. Классификатор координатора тоже уходит
на GPU, но копия в RAM остаётся, потому что она же служит таблицей эмбеддингов.
Произведения с общим входом (q/k/v, gate/up) отправляются одним пакетом: четыре
отправки на слой. Ошибка GPU не роняет узел. Стадия сообщает об ошибке, и
координатор переносит её на другой узел, как при любом отказе.

**Планирование по мощности.** Каждый узел при запуске замеряет скорость
прогона весов через умножение (ГБ/с, `MeasureSpeed`) и рассылает её вместе со
свободной памятью: у GPU-узла отдельно видеопамять под веса и RAM под кеши.
Координатор (`planStages`) считает, сколько слоёв помещается на каждом узле
для данной длины генерации; уже загруженные слои этой модели стоят только кеша.
- **Без явного числа стадий** самые быстрые узлы берут столько слоёв, сколько
  помещается. Время токена — сумма по стадиям слоёв, делённых на скорость,
  поэтому так быстрее всего, и переходов меньше.
- **С заданным числом стадий** слои делятся пропорционально скорости в
  пределах памяти.

Узел, которому не хватает памяти даже на слой, слоёв не получает. Модель, не
помещающаяся во все узлы вместе, отклоняется с объяснением. При отказе стадия
переезжает на самый быстрый из узлов, где она помещается.

Тест на кластере: узел с GPU, вмещающий два слоя, получает ровно их; узел без
памяти на слой не получает ничего; остаток уходит большому CPU-узлу; текст
совпадает с локальным.

**Скорость на этой машине** (Ryzen с встроенной Vega, общая память DDR4).
Встроенный GPU прогоняет веса со скоростью около 22 ГБ/с, а 16 потоков CPU с
AVX2 около 30 ГБ/с, так что здесь GPU медленнее:

| Qwen2.5-0.5B | CPU | Vega (RADV) | lavapipe |
|---|---|---|---|
| bf16 | 33 ток/с | 19 ток/с | 6 ток/с |
| `q4_m` | 49 ток/с | 36 ток/с | 9 ток/с |

Одна отправка команд стоит около 58 мкс. Дискретные GPU с памятью на
300–1000 ГБ/с должны обгонять CPU в разы, но проверить это было не на чем.

Ограничения: Vulkan 1.1+ и 64-битные платформы (Linux, macOS, Windows; на
FreeBSD только CPU). Один GPU на узел, произведения на нём идут по одному.

## Открытая сеть (`internal/membership`, `internal/mesh`, `internal/trust`)

Сеть открывается и закрывается без перенастройки участников:
`rakkan-node network open -pow 24` подписывает корневым ключом **политику**
(`open`, `pow_bits`, номер версии), демон с `-policy` распространяет её через
gossip и в каждом рукопожатии. Более новая политика заменяет старую. Закрытие
или повышение сложности отключает гостей, которых политика больше не пускает.
Гость, чьё доказательство устарело, сам решает новое и переподключается.

**Гость** — узел без сертификата. Он доказывает работу над своей личностью:
nonce, при котором SHA-256(домен, ID сети, peer ID, nonce) начинается с N
нулевых бит. Доказательство привязано к сети и ключу, проверяется одним хешем.
24 бита — около 6 CPU-секунд (0,4 с на 16 потоках), каждый бит удваивает цену.
PoW не делает личности дорогими — оно делает дорогой их **смену**. Вся
репутация и кредит привязаны к личности, и пойманный гость теряет их вместе с ней.
Демон без `-cert` входит гостем сам: берёт политику у bootstrap-узла (протокол
`/rakkan/policy/1.0.0` отвечает до аутентификации; подпись корня делает ответ
чужого узла безопасным), решает PoW, сохраняет его в `-proof`. Гостей можно
отзывать по peer ID тем же CRL (`network revoke <peer ID>`; так же отзываются и
участники). Гости ограничены `MaxGuests` и первыми идут под обрезку соединений.
Слоты relay им не выдаются: relay служит участникам, за которых ручается
оператор. Наблюдаемые адреса от гостей не принимаются, чтобы гость не мог
подменить адрес.

**Доверие** (`internal/trust`). Участники с сертификатами и сам узел доверены.
Гостей проверяют:

- **Задачи.** Результат гостя с вероятностью `max(0.1, 1 − репутация)`
  перезапускается на независимом узле, по возможности на участнике с
  сертификатом. Детерминизм делает сравнение точным: совпадать обязаны вывод,
  код выхода, gas и вид ошибки (ложное «out of gas» тоже ловится). Если
  второй исполнитель тоже гость и их результаты расходятся, третий запуск решает
  большинством. Разошедшийся с принятым результатом — **обманщик**. Узел,
  поймавший гостя, отключает его на 24 ч и больше не даёт ему работы. Участнику
  с сертификатом работа не даётся на тот же срок, а в лог пишется предложение
  отозвать сертификат. Явная репликация (`replicas`) тоже даёт эти свидетельства.
- **Стадии LLM.** Стадию на госте дублирует **свидетель** на доверенном узле:
  те же входы параллельно, без добавочной задержки. Выходы сравниваются побитно
  на каждом шаге. При расхождении свидетель забирает стадию (его кеш уже
  актуален), гость отмечается обманщиком, текст не меняется. Если гость упал,
  свидетель тоже подменяет его без переигрывания. Цена — двойные вычисления
  стадий гостей. Без доверенного узла с нужными слоями стадия идёт без проверки,
  с предупреждением в логе.

**Репутация** — EigenTrust (Kamvar и др., 2003). Каждый узел публикует в
gossip локальное доверие: как распределены подтверждённые результаты между
пирами (подтверждение +1, сбой −1, обман −20). Глобальное доверие
t = 0,85·Cᵀt + 0,15·p, где p сосредоточено на участниках с сертификатами;
каждый узел вычисляет t сам по полученным векторам. Доверие течёт только от
участников и тех, кому они доверяют, взвешенное доверием к источнику, поэтому
клика сибилов, хвалящих друг друга, не получает ничего сверх того, что к ней
просочилось. В тесте 20 сибилов получили 1,4% общего доверия, честные гости
по 41%. Локальное доверие насыщается на 100 подтверждениях: до этого остаток
остаётся у участников, и репутация отражает объём проверенной работы, а не
только её долю. Без насыщения один честный ответ давал гостю полную репутацию,
и дальше проверялись лишь 10% его результатов; это нашёл нестабильный тест.
Оценка гостя — его доля относительно средней (`t·n`), с потолком 1.

**Кредит** двусторонний, как tit-for-tat в BitTorrent, без общего реестра.
Узел считает gas, потраченный на каждого пира и каждым пиром на него. Гость
может «задолжать» не больше `-free-credit` (50·10⁹ gas, около 8 CPU-секунд)
плюс кредитная линия, пропорциональная репутации. Бюджет gas задачи
резервируется заранее, списывается фактически потраченный. Стадия LLM
оценивается в 8 gas на вес на токен. Вычисляя для сети, гость зарабатывает
кредит напрямую у тех, для кого считал, и через репутацию у всех остальных.
Участники не ограничены. Реестр хранится в `<data>/trust.json`, его видно
через `GET /v1/trust` и `mesh.trust()`.

Что проверено тестами: гостя пускают только в открытую сеть; повышение
сложности заставляет его перерешать PoW, закрытие сети и отзыв отключают его;
обман в задаче и в стадии LLM ловится, результат и текст остаются верными,
обманщик отключается и не получает работы; кредит кончается после двух задач
и восстанавливается вычислениями для кредитора; JS-тест с настоящими демонами:
гость берёт политику у bootstrap-узла, решает PoW, его результат проверяется.

Ограничения:
- в сети, где нет ни одного участника с сертификатом, доверие гостям
  неоткуда взять: нужно ядро, за которое ручается корень;
- гость с высокой репутацией проверяется в 10% задач; повторный обман стоит
  ему личности, но отдельный ложный результат может пройти. Тем, кому важна
  точность, нужна явная репликация (`replicas`);
- вычисления на GPU недетерминированы, побитовое сравнение для них не подойдёт:
  понадобится сравнение с допуском;
- gossip от гостей ограничен только размером: защиты от спама на уровне
  peer scoring GossipSub пока нет;
- кредит локален: узел, которому гость задолжал, не может предъявить долг
  остальным, кроме как через репутацию.
