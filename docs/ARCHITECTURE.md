# Rakkan Mesh — архитектура

Mesh-сеть для распределённых вычислений: узлы на Go, клиентский SDK для Node.js,
задачи — WebAssembly-модули, присылаемые в рантайме.

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Модель доступа | Закрытая сеть, с заделом на открытие | Убирает Sybil-атаки на старте; доверие через PKI |
| Связь Go ↔ Node.js | Демон + SDK по unix-socket (gRPC/Connect) | Нет cgo/N-API-сборки под платформы, падение демона не роняет приложение |
| P2P-слой | go-libp2p | QUIC/Noise, mDNS, Kademlia, NAT traversal, relay — готовы и проверены |
| WASM-рантайм | wazero | Чистый Go, без cgo, лимит памяти, прерывание по контексту |
| Целевой максимум | Распределённый инференс LLM | Определяет требования к планировщику и execution-классам (ниже) |

## Закрытая сеть и путь к открытой

- **Членство**: корневой ключ сети подписывает сертификаты узлов
  (`node_pubkey, roles, expiry`). Вход — по одноразовому invite-токену.
- **Отзыв**: список отозванных сертификатов распространяется через gossip, подписан корнем.
- **Транспорт**: libp2p Noise + опционально PSK (`pnet`) как второй периметр.
- **Задел на открытие**: вся логика допуска и доверия — за интерфейсом `trust.Policy`.
  Закрытая реализация: «сертификат валиден → доверяем, репутация влияет только на
  приоритет». Открытая реализация (позже): PoW-ID + EigenTrust + репликация с голосованием.
  Остальной код не знает, какая политика активна.

## Классы исполнения

Задачи сильно разные — от перебора хешей до LLM. Один механизм всё не покроет:

| Класс | Пример | Как исполняется |
|---|---|---|
| **Pure WASM** | подбор хеша, парсинг, сжатие, мелкие фильтры | Весь код в WASM, CPU-only, SIMD128 |
| **WASM + host kernels** | обработка фото, ресайз, свёртки | WASM оркеструет, тяжёлые примитивы — версионированные host-функции узла (`image.*`, `tensor.*`), объявленные как capabilities |
| **Native services** | инференс LLM, GPU-вычисления | Узел запускает доверенный нативный движок (llama.cpp/ggml-сайдкар); WASM-задача может вызывать его через capability `llm.*` |

Почему LLM не может быть «просто WASM»:
- нет доступа к GPU, а CPU-SIMD WASM в разы медленнее нативного AVX-512/AMX;
- wasm32 адресует максимум 4 ГиБ — меньше весов любой полезной модели;
- веса модели должны жить на узле постоянно, а не пересылаться с каждой задачей.

Узлы публикуют **capability-манифест**: CPU/GPU, VRAM, RAM, доступные host-kernels
(с версиями), закешированные модели/слои. Планировщик выбирает узлы по нему.

## Распределённый LLM (план-максимум)

- **Pipeline parallelism по слоям** (подход Petals/exo): каждый узел держит
  диапазон слоёв, активации передаются по цепочке. Активация на токен — это
  `hidden_size × 2 байта` (≈8–16 КБ), что приемлемо даже для WAN. Tensor parallelism
  требует широкого канала, поэтому годится только внутри одной LAN или машины.
- **Задержка** на токен ≈ сумма хопов → планировщику нужна карта задержек
  (координаты Vivaldi) и выбор цепочки с минимальным суммарным RTT.
- **Отказоустойчивость**: каждый диапазон слоёв держат ≥2 узла. При падении
  узла цепочка перестраивается, KV-кеш на замене восстанавливается повторным
  prefill уже сгенерированного контекста.
- **Веса**: content-addressed, порезаны по слоям, раздаются внутри сети по
  принципу BitTorrent. Узел скачивает только свои слои.
- **Верификация**: GPU-вычисления недетерминированы (неассоциативность float),
  побайтовое сравнение реплик не работает. В закрытой сети — доверие по
  сертификату; для открытой — сравнение с допуском (logits/top-k) и выборочная
  перепроверка.

## Модель задач

- **Task** — один вызов WASM-модуля: `(module_hash, entry, input, limits, capabilities)`.
- **Job** — граф задач: map/reduce, DAG. Перебор хеша = map по диапазонам
  с ранней отменой остальных, когда ответ найден.
- **Данные** отделены от управления: модули и большие входы (фото, веса) лежат
  в content-addressed хранилище и передаются потоками; в сообщении о задаче —
  только хеши.

## WASM-песочница (`internal/sandbox`)

Реализовано:
- единственное разрешённое пространство импортов `rakkan` (`input_len`,
  `input_read`, `output_write`, `log`); WASI, импорт памяти и чужие модули
  отклоняются до инстанцирования — у гостя нет часов, ФС, сети, случайности;
- лимит линейной памяти на задачу (`memory.grow` сверх лимита возвращает -1);
- **детерминированный gas** (`internal/meter`, расписание стоимостей v1): модуль
  переписывается при загрузке — каждый линейный сегмент кода платит свою точную
  стоимость при входе, проверки стоят на входе в функцию, в заголовках циклов и
  на bulk-операциях (`memory.fill/copy/grow`, table-*), которые тарифицируются по
  длине; вызовы хоста тоже платят. Накладные расходы ≈1,7× на плотном цикле;
- таймаут и отмена доставляются через флаг прерывания, который проверяется вместе
  с gas (гость его только читает, поэтому запись сторожа не теряется), без
  `WithCloseOnContextDone`, который замедляет циклы wazero ~30×;
- полный разбор всех секций до передачи в wazero: декодер wazero 1.12
  предвыделяет память по объявленным счётчикам, и модуль из 26 байт мог положить
  процесс узла (OOM);
- лимиты на размер модуля, входа, выхода, лога;
- политика узла (`Limits.Within`): клиент не может запросить больше, чем разрешил оператор.

- **структурные лимиты** (`meter.Max*`): вложенность ≤ 1024, `br_table` ≤ 16 384
  целей, ≤ 4 таблиц по ≤ 2¹⁸ элементов (объявленный `max` урезается), одна
  память без shared/64-bit, ≤ 128 параметров/результатов, ограничения на число
  типов, импортов, функций, глобалов, экспортов, сегментов, локальных, размер тела.
  Компилятор wazero сверхлинеен по вложенности, `br_table` и «локальные × ветвления»;
  модуль на 30 КБ мог компилироваться секунды, а на 300 КБ — минуты. Лимиты срезают
  худшие соотношения, а компиляция засчитывается в таймаут задачи: узел убьёт
  воркер, если она не уложится. Компиляция может требовать и сотни мегабайт —
  это останавливает лимит памяти воркера (`ErrWorkerOOM`);
- **кеш**: `Runner` хранит инструментированные модули (LRU, 64 МБ) и
  скомпилированный код wazero, поэтому повторный запуск модуля в том же процессе
  пропускает и инструментацию, и компиляцию.

- **канонизация NaN**: после каждой операции, способной породить NaN
  (арифметика, округления, demote/promote, их SIMD-версии), результат заменяется
  каноническим NaN, если он NaN. Без этого 0/0 даёт 0xffc00000 на x86 и
  0x7fc00000 на ARM — узлы разной архитектуры расходились бы побайтово. Вместе с
  gas это ≈1,37× на плотном float-цикле.

Найденные проблемы wazero описаны для отправки в `docs/upstream/wazero-issues.md`.
5. **Capabilities**: host-kernels (`image.*`, `tensor.*`, `llm.*`) выдаются
   задаче явно и тарифицируются в gas.

## Изоляция процессов (`internal/isolate`)

Узел исполняет задачи не у себя, а в воркерах — это повторный запуск того же
бинарника (`isolate.IsWorker` / `RunWorker`). Пул держит свежие процессы «тёплыми».

`Pool.Run(ctx, owner, task)`: задача без владельца идёт в процесс, который ещё
ничего не исполнял. Задачи с владельцем могут переиспользовать процесс, уже
исполнявший **тот же модуль для того же владельца** (до `TasksPerWorker` задач,
простаивающие отпускаются через `IdleTimeout`) — повторный запуск тогда идёт без
старта процесса, инструментации и компиляции (на тестовом модуле 588 мс → 1,2 мс).
Процессы никогда не делятся между владельцами или модулями: задача, захватившая
воркер, достанет лишь данные, которые её владелец и так отдавал тому же коду.

Общий файловый кеш скомпилированного кода между процессами сознательно не
сделан: это исполнение машинного кода, записанного процессом, который
компилировал недоверенный модуль. Безопасная схема (компиляция в отдельном
свежем процессе, хранение по хешу модуля, вычисленному узлом, видимость только
задачам того же модуля) упирается в непубличный формат ключей кеша wazero.

Слои (`Isolation`):
- **namespaces**: user, mount, PID, network, IPC, UTS. Корень — пустой tmpfs
  только для чтения, в нём лишь бинарник воркера (и загрузчик с libc, если
  бинарник динамический). Сети нет совсем.
- **никаких capabilities**: воркер стартует root-ом своего user namespace,
  готовит корень, ставит securebits `NOROOT` и делает re-exec — после этого
  capabilities пусты во всех потоках. (Сбросить их иначе нельзя: capset
  действует на поток, а `AllThreadsSyscall` недоступен, когда слинкован cgo.)
- **seccomp-bpf**: allow-list того, что нужно рантайму Go и JIT (память, потоки,
  сигналы, часы, I/O на уже открытых дескрипторах). `open` → EPERM, `clone`
  разрешён только для потоков, всё остальное (сокеты, fork, mount, ptrace, bpf…)
  убивает процесс.
- **rlimits**: core, fsize, nofile, memlock; без cgroup — лимит адресного
  пространства.
- **cgroup v2** (опционально): `memory.max` без swap, `oom.group`, `pids.max`,
  `cpu.max`; воркер попадает в свою cgroup атомарно при clone
  (`CLONE_INTO_CGROUP`). OOM распознаётся и возвращается как `ErrWorkerOOM`.

Узел не доверяет ответам воркера: размеры и gas сверяются с лимитами задачи,
жёсткий дедлайн (таймаут + 2 с) убивает зависший воркер, падения
классифицируются (в том числе «убит seccomp»).

Особенность Go: скомпилированный WASM нельзя вытеснить, поэтому stop-the-world
фаза GC, начавшаяся во время работы гостя, ждёт его окончания вместе со всеми
горутинами. В воркере GC на время задачи выключен (память держат cgroup/rlimit).
Внутрипроцессный `sandbox.Runner` поэтому годится только для локальных запусков,
но не для узла.

Запуск с cgroups: узлу нужна делегированная ему одному cgroup, например
`systemd-run --user --scope -p Delegate=yes rakkan-node …` или `Delegate=yes`
в unit-файле, и параметр `-cgroup self`. Тест: `RAKKAN_TEST_CGROUP=1` внутри
такой cgroup (см. `TestCgroupLimits`).

## Сеть (`internal/membership`, `internal/mesh`)

**Членство.** ID сети — peer ID корневого ключа (Ed25519 встроен в ID, так что
строка ID и есть якорь доверия). Корень подписывает сертификаты узлов:
`{сеть, peer ID, роли, серийный номер, срок}`. Узел с ролью `admin` может
выпускать сертификаты участников без корневого ключа, но не админов — цепочка не
длиннее двух звеньев, и делегированный сертификат не переживает сертификат
админа. Отзыв — подписанный корнем кумулятивный CRL с возрастающим номером;
отзыв админа аннулирует всё, что он выпустил. Подписи разделены по доменам
(сертификат нельзя выдать за CRL и наоборот). Сертификат доказывает членство
только вместе с соединением: libp2p аутентифицирует peer ID, и он обязан
совпасть с субъектом.

**Допуск.** Сразу после соединения стороны обмениваются сертификатами (и своим
последним CRL) по `/rakkan/auth/1.0.0`. Кто не прошёл за `AuthTimeout` — отключён
и временно заблокирован гейтером соединений; отозванный — навсегда. Все
прикладные протоколы (DHT, pubsub и протоколы, зарегистрированные через
`Node.Handle`) видят хост-обёртку, пропускающую потоки в обе стороны только для
аутентифицированных участников: посторонний не может даже спросить у DHT адреса
участников.

**Обнаружение.** Bootstrap-узлы, mDNS в локальной сети, приватная Kademlia DHT
(свой префикс протокола, в таблице маршрутизации только участники) с
rendezvous-записью сети. Раунды поиска начинаются каждые 2 с и замедляются до
`DiscoveryInterval`; допуск нового участника запускает раунд сразу.
(`util.Advertise` из libp2p не годится: после первой неудачи на пустой таблице
он ждёт 2 минуты.)

**Восстановление.** Ping участников с измерением RTT; три пропуска подряд —
соединение закрывается. Известные участники переподключаются с экспоненциальной
задержкой и джиттером (до `MaxBackoff`), свежие адреса ищутся в DHT. Узел,
вернувшийся на тот же адрес, будет найден без его участия. Сертификаты живых
участников перепроверяются: истёкший или отозванный отключается.

**NAT.** UPnP, hole punching (DCUtR), relay v2 через участников с `-relay`
(ACL пускает только участников). Стандартная автоматика libp2p рассчитана на
большую публичную сеть и в маленькой закрытой не работает — это показала
NAT-лаборатория, поэтому:
- *достижимость* определяется по адресам прослушивания (публичный адрес —
  публичный узел, только приватные — за NAT), а не AutoNAT: тому нужны несколько
  проверяющих, а единственный проверяющий звонит обратно по тому же 5-tuple, NAT
  пропускает, и узел за NAT считает себя публичным. Переопределяется флагом
  `-reachability`;
- *relay-сервис* при `-relay` запускается сразу, а не после подтверждения AutoNAT;
- *AutoRelay* довольствуется одним кандидатом, без 3-минутной задержки, и
  кандидаты — только участники, реально поддерживающие relay;
- *внешний адрес* узла за NAT сообщают в обмене сертификатами аутентифицированные
  участники (хватает одного). Своему механизму libp2p нужны 4 наблюдателя, и
  учитывает он любого подключившегося;
- loopback-адреса не публикуются (иначе другие звонили сами себе);
- *кеш участников* (`-peers peers.json`) переживает перезапуск: узлы
  возвращаются в сеть, даже когда все bootstrap-узлы лежат.

**NAT-лаборатория** (`test/natlab`) — эмуляция интернета, роутеров с NAT и
машин за ними в network namespaces одного непривилегированного user namespace
(root не нужен). NAT `cone` — обычный masquerade с сохранением порта, как у
домашних роутеров; `symmetric` — новый порт на каждое направление, как у CGNAT.
`test/natlab/run-all.sh <бинарник>` проверяет:

| Сценарий | Результат |
|---|---|
| cone ↔ cone | прямое соединение (hole punching) |
| cone ↔ symmetric | через relay |
| symmetric ↔ symmetric | через relay |
| якорь падает после установления связи | прямое соединение сохраняется |
| оба узла перезапущены, якорь лежит, с кешем | прямое соединение восстановлено |
| то же без кеша | изоляция (контрольный прогон) |

**Отзыв в работе.** Оператор выполняет `network revoke`, переписывая `crl.json`;
демон, запущенный с `-crl crl.json`, замечает новую версию, публикует её через
GossipSub (валидатор проверяет подпись корня), и вся сеть отключает отозванного.
CRL также передаётся в каждом обмене сертификатами, так что новые и вернувшиеся
узлы узнают о нём при подключении.

Пример:

```sh
rakkan-node network init -out root.key            # печатает ID сети
rakkan-node id -key n1.key                         # на каждом узле: его peer ID
rakkan-node network issue -peer <id1> -roles member,admin -out n1.cert
rakkan-node network issue -key n1.key -issuer-cert n1.cert -network <net> -peer <id2> -out n2.cert
rakkan-node daemon -network <net> -key n1.key -cert n1.cert -crl crl.json
rakkan-node daemon -network <net> -key n2.key -cert n2.cert -bootstrap /ip4/…/tcp/…/p2p/<id1>
rakkan-node network revoke -crl crl.json <serial>  # серийный номер: network show <cert>
```

## Распределённое исполнение (`internal/exec`, `internal/api`, `sdk/js`)

**Протокол `/rakkan/exec/1.0.0`**, одна задача на поток: заголовок (хеш модуля,
размеры, лимиты) → предложение исполнителя (`send_module` / `ready` / `busy` /
`rejected`) → модуль (только если его у исполнителя нет) и вход → результат.
Модули адресуются по SHA-256: исполнитель проверяет хеш присланного модуля и
кеширует его, так что повторные задачи передают только вход. Владелец задачи для
пула воркеров — peer ID отправителя: его задачи с тем же модулем переиспользуют
тёплый воркер. Отправитель держит поток открытым до результата; сброс потока
отменяет задачу у исполнителя.

**Загрузка** узлов (слоты, занятость, очередь, лимиты, CPU, архитектура)
распространяется через GossipSub раз в несколько секунд и сразу после изменений.

**Планировщик** работает у отправителя: среди участников (и себя), чьи лимиты
допускают задачу, выбирается узел с наибольшим числом свободных слотов, при
равенстве — уже имеющий модуль, затем с меньшим RTT; себе — небольшой бонус (нет
передачи). Свои задачи «в полёте» к каждому узлу учитываются сразу, не дожидаясь
госсипа. Если все заняты — ожидание; если лимиты задачи превышают политику всех
узлов — ошибка с объяснением.

**Отказоустойчивость.** Сбой исполнителя (обрыв, падение воркера, нарушение
протокола, остановка узла) — повтор на другом узле, до `MaxAttempts`. «Занят» не
считается попыткой. Детерминированные ошибки задачи (gas, trap, таймаут,
некорректный модуль) не повторяются — любой узел выдал бы то же. Исполнитель,
прервавший задачу по своей причине, не отправляет «отменено» как результат, а
сбрасывает поток.

**Репликация.** `Replicas: k` — задача на k разных узлах; сравниваются код
выхода, gas и SHA-256 вывода (или вид ошибки). Принимается исход большинства от
k, несогласные реплики помечаются. Это работает благодаря детерминизму фазы 1:
gas и NaN побайтово совпадают на разных машинах и архитектурах.

**Map** — один модуль на много входов с ограничением параллелизма (по умолчанию
— свободные слоты сети), результаты потоком; `StopWhen` останавливает и
отменяет остальное.

**Локальный API** — HTTP на unix-сокете с правами 0600: `/v1/modules`,
`/v1/run`, `/v1/map` (NDJSON-поток), `/v1/status`. Разрыв соединения отменяет
задачи. **JS SDK** (`sdk/js`) — ESM без зависимостей с типами TypeScript.

Пример (`sdk/js/examples/search.js`, 3 узла по 4 воркера на одной машине):
поиск прообраза хеша среди 2³⁰ значений, 1024 диапазона — найден за 0,47 с,
после 873 диапазонов остальные отменены.

## Данные (`internal/blob`)

**Блобы с адресацией по содержимому.** Данные режутся на чанки по 1 МиБ, каждый
назван своим SHA-256; манифест — размер и список хешей чанков, ID блоба —
SHA-256 манифеста. Отсюда: каждый чанк проверяется при получении (данные от
недоверенного узла проверены до записи на диск), одинаковые чанки хранятся
один раз, прерванная загрузка продолжается с полученных чанков, чанки можно
брать у нескольких узлов одновременно.

**Хранилище** на диске (`-data`, бюджет `-store-gb`): вытесняются давно не
использованные блобы, кроме закреплённых (используемых задачами и загрузками).
Чанки незавершённой загрузки сохраняются для докачки — и после перезапуска
узла, — но вытесняются первыми и удаляются через час. Пока блоб собирается, его
чанки удерживаются, чтобы вытеснение другого блоба с общими чанками их не
удалило.

**Передача** `/rakkan/blob/1.0.0`: манифест, затем пачки по 8 чанков; до двух
потоков на источник, не больше 8 всего. Пачка, которая не пришла, пришла не
целиком или с испорченным чанком, уходит другому источнику; источник после трёх
неудач исключается. Одновременные загрузки одного блоба объединяются. Любой
участник может получить блоб, если знает его ID — ID это хеш содержимого.
На одной машине (loopback, QUIC): ≈415 МБ/с с одного источника, ≈512 МБ/с с двух
— упор в CPU (шифрование и SHA-256), а не в сеть.

**В задачах.** Вход больше 1 МиБ отправитель сохраняет как блоб, исполнитель
забирает его у отправителя (и у перечисленных источников); выход больше 1 МиБ
исполнитель сохраняет как блоб, отправитель сразу забирает его, так что
результат не зависит от того, останется ли исполнитель в сети. Реплики
сравнивают ID выхода — он одинаков для одного содержимого, пришло ли оно
блобом или в сообщении. Воркер по-прежнему получает вход целиком (в пределах
`MaxInputBytes`; у изолированного воркера нет файловой системы), поэтому бюджет
памяти воркера учитывает потолки входа и выхода (`-max-input-mb`,
`-max-output-mb`).

**API/SDK.** `POST /v1/blobs` пишет тело запроса в хранилище по чанкам, не
держа его в памяти; `GET /v1/blobs/{id}` поддерживает Range. SDK: `putBlob`
(байты, поток, `{path}`), `getBlob` (поток, диапазоны), `readBlob`; `run`
сам загружает вход больше 256 КБ блобом и скачивает выход-блоб, если не
указан `outputAsBlob`.

Что дальше: задачи с общими большими данными (один блоб для многих задач map,
например модель или словарь, читаемый через host-функцию, а не копией во
входе), поиск источников блоба через DHT, квоты и приоритеты между владельцами,
учёт ресурсов (кредиты), host-kernels (изображения, тензоры), очередь задач,
переживающая перезапуск отправителя.

0. ✅ Каркас, песочница v0, CLI `rakkan-node run`.

   map с ранней остановкой, локальный API, JS SDK; хранилище данных с
   адресацией по содержимому и потоковой передачей больших входов и выходов.
4. Host-kernels: изображения, тензоры. Примеры на AssemblyScript/Rust.
5. Native services: LLM-сайдкар, pipeline по слоям, раздача весов.
6. Открытие сети: PoW-ID, EigenTrust, репликация с голосованием, кредиты.
